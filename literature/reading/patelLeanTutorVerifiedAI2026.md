## 1. 一句话定位

LeanTutor 是一个**概念验证级的证明导师**：学生用自然语言写证明（可以是不完整、甚至是错的），系统用 Lean 在后台判定对错、生成**下一条合法 tactic**、并用自然语言给出**不泄露答案的引导性反馈**。它的核心贡献不是"更强的证明器"，而是把 autoformalization 的目标从"翻译"改成**"忠实还原"（faithful autoformalization）**，并且**在导师场景下把这个问题变简单**（有参考解答、定理库很小），同时给出一条**可复现的评估口径**与一个新的忠实性度量。

## 2. 问题与动机

论文把"学生为什么用 LLM 反而学不好"列成四条（§1 引多篇工作）：(1) 模型被设计成**最大程度"有用"**，于是**直接把答案给掉**而不是帮学生自己想出来；(2) **SOTA 模型仍会幻觉、会生成有说服力的错误答案**；(3) **模型不擅长定位推理中的错误**；(4) **即使能给出正确答案，也不一定能给出正确的推理来引导学生**。教师侧的担心集中在"批判性思维"是核心目标的证明课。

已有的数学证明导师分三类，各有硬伤（§2.4）：

- **智能导师系统（ITS）**：确定正确，但**需要专家手工编写解答与反馈**，难开发难扩展；
- **LLM 导师**：有学习增益的证据，但上述四条问题；
- **基于定理证明器的导师**：确定正确（如 Lean），但**学生要学复杂语法**，或者被限制在应用专用的受控自然语言里。

LeanTutor 的定位是**组合两者的互补优势**：与学生用自然语言交互，用 Lean 在后端判正确性与生成下一步。

**导师场景带来的四个"更简单"（这是本文最有价值的分析，§1 末尾）**：

1. **忠实性优先于覆盖率**：导师场景的 autoformalization 必须**保留语义**，而自然语言证明与形式证明在写法上有两个根本差异——**形式证明比非形式证明细粒度得多**（人类认为严谨的一步，比如"由对称性"，在形式语言里可能需要冗长证明）；**非形式证明常用前向推理，形式证明常靠后向推理**。
2. **语法正确 ≠ 语义忠实**：`syntactic correctness (i.e. successful compilation) is insufficient`（引 Liu et al. 2025）。
3. **必须处理不完整与错误的证明**，而学生自然语言变体极多、且没有专业数学写作的打磨；此前的 autoformalization 工作主要针对**定理陈述**与**正确完整证明**。
4. **导师场景可以假设"教师知道一份完整解答"**——这是**忠实 autoformalization 的一个更容易的版本**，论文明确说这提高了性能，并把"如何充分利用参考解答"留作未来问题；同理，**下一步生成的搜索空间可以限制在很小的定理库里**，而不是像 novelty 证明搜索那样面对 Mathlib 这样的巨型库。

## 3. 记忆结构

**PeanoBench**（§3）是这个系统的"语料 + 参照记忆"：

- **总规模 371 条证明**，每条同时有人写的自然语言版本（NL）与语义等价的 Lean 形式版本（FL）。
- 来源：**Natural Number Game 4（NNG4）原有的 80 条 Peano 算术（PA）证明**（Apache-2.0），取其中 **75 条**做**回译（back-translation）**（借低资源机器翻译的做法）；**全部 NL 注释由论文前五位作者撰写**。
- **两条注释规则**：(1) NL 注释**不含任何 Lean 专有语法、前提或 tactic**；(2) 注释写成**可独立于 Lean 代码成立的证明**。
- **区别于先前数据集的关键**：**NL 证明步与 FL tactic 之间是一一对应的**（prior work 是整篇 Lean 证明对整篇 NL）。
- **正确证明 225 条**，分三组：
  - **staff-solution**：直接来自 NNG4，由两位作者注释、注释非常详尽；**只作为上下文提供给模型，不参与性能评估**；
  - **equation-based persona**：NL 主要由代数变形构成、**词很少**；
  - **justification-based persona**：NL 里**显式包含所用到的定理与数学定义**。
  后两组按"**人物设定（personas）**"生成（该技术在 UI 设计与人造数据生成里都用）；每条由一个注释者写、由**另一个**注释者校对；在可能时**除了改 NL 注释还改动了 Lean 代码本身**（可以是重大逻辑差异，也可以是重新排列交换律类 tactic）。
- **错误证明 146 条**（数学上 225 + 146 = 371 恰好自洽）：构造方式是**模仿逻辑错误**——学生在归纳证明中常见的一类错误是"认为证明有效但其实无效"（引 Weber 2001），典型例子是**假设了 P ⟹ Q 却忘掉这一步需要理由**；论文的做法是**随机从证明的最后三行里跳过一步**。一行长的证明从错误集里剔除。
- **论文自己列的两条局限**：(a) 这只覆盖一种错误类型，**不能代表学生犯的所有错误**；(b) **程序化删除可能产生不现实的错误**。
- **评估口径**（重要）：**staff-solution 只作上下文**，性能在 equation-based 与 justification-based 的正确与错误证明上评。

## 4. 写路径（固化）

三个模块的"写入"都指向学生证明的**逐步形式化**，机制如下。

### 4.1 Autoformalizer / proof checker（§4.1）

- **逐步**：一次只形式化**一个学生证明步**，每一步都做编译检查；把该步的形式化结果**追加到 Lean 定理陈述与之前已形式化的步骤之后**再编译。流程重复到"学生写完"或"学生出错"为止（Figure 2）。
- **模型**：通用 LLM 提示（`gpt-4o-mini-2024-07-18`，temperature 0.0）。**明确不做开源模型的微调或推理**，理由是**面向整篇证明 autoformalization 的开源模型严重不足，且 PeanoBench 规模太小**。
- **上下文里放四样东西**：
  1. **Staff Solution**：一份**同时有 NL 与 FL** 的参考证明（**可能与正在形式化的学生证明不一致**）；论文明确说**目前只把它放进上下文，没有进一步利用**，留作未来工作；
  2. **Theorem and Tactic Dictionary**：数据集中**全部**定理与 tactic 的字典，**键是 Lean 形式名、值是自然语言描述**；
  3. **5-shot 示例**（照 Murphy et al. 2024）；
  4. 学生输入。
- **判错规则（这是全文最硬的机制）**：
  - 若编译器输出**只有 unsolved goals** → 认为该学生步**正确**，继续形式化后续步骤；
  - 出现**任何其他错误消息**（unknown tactic、unexpected identifier 等）→ 认为该学生步**错误**，**标记该步为 erroneous**；
  - **定位到第一个错误就结束 autoformalization**；
  - **论文明确承认的歧义**：编译器错误**既可能是学生步骤错，也可能是 autoformalization 错**（`a limitation of the system that we intend to address in future work`）。
- **度量（§5.1，忠实 autoformalization 的新度量）**：**relaxed exact matching**，两阶段：
  1. **exact tactic-matching**：生成的 tactic 字符串与 ground truth 字符串直接匹配；
  2. 失败则 **state-matching**：分别把预测 tactic 与真值 tactic 追加到各自的（预测/真值）证明上，检查得到的 **proof state 是否在变量重命名意义下语法相同**。为处理变量名差异，proof state 按 goal / casework 分段，用自写的 Python 实现对 Lean 标识符的定位，把各段里的变量标准化后再做字符串匹配。
  3. 两阶段都失败 → 判为**不忠实的 autoformalization**。
  论文选这套而不选 LLM-as-a-judge（会有幻觉、不可靠）或 SMT 等价证明（Murphy et al. 2024），理由是**它们要么太粗（Murphy / Liu），要么依赖昂贵工具**；本文**主要依赖人工评价**。

### 4.2 Next Step Generator / NSG（§4.2）

- **触发条件**：当 autoformalizer/proof checker **没有判定学生证明"完整且正确"**时启动。
- **输入**：**已形式化的部分学生证明，且把出错的那一步移除**。
- **目标**：输出**一条能导向完整证明的 Lean tactic**。
- **机制**：**LLM 引导的深度优先证明搜索**（照 COPRA，Thakur et al. 2023）：
  1. LLM **生成 12 条候选 tactic，并给出"成为正确下一步"的可能性排序**；prompt 里带上**该定理所在 NNG4 world 的全部 tactic/premise 列表**；
  2. 12 条候选**追加到现有证明**后过 Lean 编译器（via **LeanInteract**）；
  3. 编译通过的候选再过 **progress check**（照 Thakur et al. 2023 与 Sanchez-Stern et al. 2020）：
     - **禁止使用"禁列"里的定理**——这张禁列**包含当前正在证的定理**，以及**按 NNG4 定义的顺序在该定理之后才引入的定理**；
     - **避免循环 tactic**（会使证明树回到已访问的 goal state）；
  4. 用通过编译与 progress check 的全部 tactic 建**证明搜索树**，深度优先搜索直到找到完整证明；
  5. **树深上限为 8**（论文说对大多数证明够用）；
  6. **找不到就把这件事报给下一个模块**。

### 4.3 Natural language feedback generator（§4.3）

- **输入**：学生**已形式化**的证明 + **Lean 编译器的错误信息**（若有）+ **NSG 生成的下一条 Lean tactic**。
- **上下文辅助**：prompt 里放入**学生在归纳证明里常犯的六类错误**（引 Baker 1996）。
- **输出三种反馈**（照 ITS 的惯例）：
  1. **指出学生的错误**；
  2. **生成一个引导性的提示或问题**（引导学生自己走到下一步）；
  3. **给出一条显式的下一步**（对应 Suzuki et al. 2017 的 bottom-out hint），论文承认**这与自动定理证明里的 auto-informalization 任务非常相似**。

## 5. 读路径（检索）

- **NSG 的"检索"是受限的库**：prompt 只放**该定理所在 NNG4 world 的 tactic/premise 列表**，并把 **NNG4 顺序里位于该定理之后的定理**和**当前定理自身**列入**禁区**。这是"**可达性 + 时序约束**"的一种廉价实现：**不该用的东西不去检索、也进不了候选**。
- 这直接印证论文 §1 的第 4 点：**导师场景可以把下一步搜索限制在小定理库里**，因为教师知道解答。
- **我们的读路径**：论文未涉及多轮检索或排序；三个模块之间是**单向数据流**（形式化 → 下一步 → 反馈），反馈不回流到检索。

## 6. 组织与关系

- **组织维度一：正确证明的三个 persona**（staff-solution / equation-based / justification-based）——**同一道题的多种等价写法**，用来测 NL 变体对形式化的影响；
- **组织维度二：正确 vs 错误证明**；
- **组织维度三：每一步的"该不该形式化/形式化成什么"由模型在上下文中决定**（没有显式分类法）；
- **关系**：NL 步骤 ↔ FL tactic 的**一一对应**是唯一的跨模态关系；禁列表（当前定理 + NNG4 顺序之后的定理）是唯一的**禁用关系**；
- **没有图结构**：不存在跨证明的依赖图或引用图。**这与 Danus 的事实图形成强对照**——LeanTutor 的复用单元是"**参考解答 + 小库**"，不是"累积的事实网络"。

## 7. 维护与自改进

- **没有在线学习或自动演进**：PeanoBench 是一次性构建的固定数据集；三个模块都是提示 + 固定模型（gpt-4o-mini）。
- **改进点是显式的未来工作清单**（§7）：
  - **更有效地利用形式/非形式的参考证明**（在 Autoformalizer 与 NSG 里）——论文承认**staff solution 目前只被放进上下文**；
  - **在下一步生成里实现回溯**：丢弃不可行的学生步骤，从学生证明中**最近一个仍能导向完整证明的位置**重新生成下一步；
  - 忠实 autoformalization 因**粒度差异**与**推理方向差异**（前向 vs 后向）而来的开放问题；
  - 人因（human factors）：论文说导师应用**强迫关注**人机联合系统中的人因，本论文未聚焦。
- **自动化的边界被明确写出**（Limitations）：
  - **不能泛化**：NL 步与 FL tactic 的**一一对应**假设在更复杂的证明上一般不成立；
  - **依赖已经形式化的 staff solution**——如果没有好的 autoformalizer，这对教师是**显著负担**；
  - **忠实性度量只在存在 ground-truth 形式化时可用**；
  - 错误证明数据集只覆盖"漏步"一种错误；**全部 NL 由论文作者而非真实学生撰写**；
  - **最关键的一条**：**如果 autoformalization 失败，系统可能给出错误反馈或无法回应学生**；因此**端到端评估时排除了 autoformalization 错误的证明**；并且**"把 Lean 编译器报错当作学生错"这个假设本身可能因 autoformalization 错而产生假阳性**（论文说抽查显示问题不大）。

## 8. 验证与质量门控（重点）

### 8.1 三模块的完整契约（逐项）

| 模块 | 输入 | 输出 | 判定者 | 失败时的行为 |
|---|---|---|---|---|
| **Autoformalizer / proof checker** | 学生 NL 证明的一步 + Lean 定理陈述 + 之前已形式化的步骤 +（staff solution、tactic/定理字典、5-shot） | 该步的 Lean 形式化；或"该步错误" | **Lean 编译器**（via LeanInteract） | 只有 unsolved goals → 判该步对；其他任何错误 → 判该步错，**在该步终止形式化** |
| **Next Step Generator** | 已形式化、**已移除出错步**的部分学生证明 + 该 world 的 tactic/premise 列表 | **一条**能导向完整证明的 Lean tactic | **Lean 编译器 + progress check + DFS 到深 8** | 树内找不到完整证明 → **把"找不到"报给反馈模块**（不伪造下一步） |
| **Feedback Generator** | 已形式化证明 + Lean 错误信息 + NSG 给出的下一条 tactic | **三类** NL 反馈：错误识别 / 提示或问题 / 显式下一步 | **人工评估**（两名助教，四轴 5 分制） | 无被评估的失败路径（autoformalization 错的样本被排除在端到端评估外） |

### 8.2 失败模式与"拒绝时的反馈内容"

- **判错规则的粗粒度是一个真正的质量风险**：所有非"仅剩未解 goal"的错误都被当成**学生错**。论文承认**编译器错误也可能来自 autoformalization 错**，这就是一个**未解决的假阳性来源**。
- **反馈是"引导"而不是"判定"**：没有"你的证明我拒绝"这一步，而是给出**错误定位 + 提示/问题 + 一条显式下一步**。三者并列，且**显式下一步必须不泄露完整答案**——这由评估轴 **Answer Leakage** 度量（最高分 5 = **完全不泄露答案**；论文预期"next step"类反馈的 leakage 分数**低是正常的**，甚至说 **1 分是预期值**）。
- **NSG 的失败也被显式上报**（"找不到完整证明"→ 交给反馈模块），也就是**"我推不出下一步"是一个一等结果**，不是沉默。

### 8.3 权限边界

- **判定权限 100% 在 Lean 编译器**：模型只负责产生形式化、tactic 候选与自然语言。
- **但"这一步是不是学生的错"这个最终判定的输入只有编译器**，没有第二意见（没有独立的 autoformalization 校验器），这就是它最弱的一环——**和 SAFE 一样，它把"表达失败"与"内容错误"混在同一个错误通道里**（区别是 SAFE 至少把它们分成两个状态）。
- **禁列表是一道硬边界**：不许用当前定理自证（**不许循环论证**），不许用 NNG4 顺序里尚未引入的定理（**不许用"以后才学的"东西**）。这两条都是**结构性**的（候选在进证明树之前就被过滤），不是提示式禁令。

### 8.4 真实质量数字（人工评估，§5.4）

评估对象：**PeanoBench 中"被成功 autoformalize"的 44 条错误证明里，每个 world 随机取 1–3 条，共 21 条**；基线是"把错误的学生证明直接给 LLM，要求生成三类反馈"。两名**有数学课教学经验的计算机系研究生**评分，事先给同一份评分协议并简短培训；**评估是 model-blind**（评分者不知道哪份来自哪个模型），**每条证明的反馈只由一名评分者评**（每人评一半）。

| 反馈类型 | 指标 | Baseline | LeanTutor |
|---|---|---|---|
| Error Identification | Accuracy / Relevance / Readability / Answer Leakage | 3.4 / 3.5 / 4.5 / 4.6 | **3.4** / **3.8** / 4.3 / 4.5 |
| Hint/Question | 同上 | 3.1 / 2.9 / 4.7 / 4.3 | **3.7** / **3.7** / 4.7 / 4.4 |
| Next Step | 同上 | 2.8 / 2.9 / 4.6 / 2.2 | **3.7** / **3.9** / 4.4 / **1.1** |

- **结论**：LeanTutor 在 **Accuracy** 与 **Relevance** 上胜出；**Readability** 与 **Answer Leakage** 两者相当。
- **一个必须注意的解读**：**Next Step 的 Answer Leakage 从 2.2 掉到 1.1，是"更泄露答案"的方向**——但论文说这在预期之内（给出显式下一步按定义就会泄露），**且这正是第三类反馈的设计目的**。所以这条"变差"不是缺陷，**是设计取舍被如实报出**。
- **一个方法论负面发现（对我们极有价值）**：论文**同时**用 gpt-4 当裁判重跑了同一评估，把 judge 校准到作者给出的三条反馈分数上。结果是**基线在几乎每个轴、每种反馈上都压过 LeanTutor**，**与人工评分不一致**。论文据此指出 LLM-as-a-judge 这个范式有问题。**这是"用模型审查代替人工审查"的一个真实反例，且出自一篇做 AI 导师的论文。**

### 8.5 忠实性度量的"准确性/召回"类数字（§5.2）

评估口径：**全部 pass@1**（与某些先前工作在 pass@8 上评估相反）；tactic 级共 **900** 条 tactic，正确证明 **150** 条，错误证明 **146** 条。

| 实验 | Correct Tactics | Correct Proofs | Incorrect Proofs |
|---|---|---|---|
| Baseline | 32.9% ± 3.1% | 6.7% ± 4.0% | 14.4% ± 5.7% |
| **Baseline + Staff Solution** | **56.8%** ± 3.2% | **18.0%** ± 6.1% | **30.1%** ± 7.4% |
| Baseline（整篇证明一次形式化） | 28.2% ± 2.9% | 10.7% ± 4.9% | 13.0% ± 5.4% |
| Baseline + Staff Solution（整篇证明） | 51.8% ± 3.3% | **26.7%** ± 7.0% | 21.9% ± 6.7% |

- **误差棒是 Jeffreys 先验的 95% 置信区间**（二项）。
- **正确证明的定义**：该证明中**全部** NL 陈述都按正确顺序被形式化成正确 tactic（因此 proof 级门槛远高于 tactic 级）。
- **错误证明的成功定义**：**(1) 第一个错误步之前的全部步骤都被正确形式化，且 (2) 对该错误步的形式化导致 Lean 编译器报错。**
- **staff solution 的巨大影响（§5.2 Findings，这组数字最值得记住）**：
  - **89%** 的正确 tactic 形式化里，预测出的 tactic **出现在 staff solution 中**（可能在别的位置）；
  - 当 autoformalization **错**时，模型**在 51% 的情况下抄了 staff solution 里的一条 tactic**，而不是预测对应 NL 输入的真实 tactic；
  - 当期望的形式化**不在** staff solution 里时，LeanTutor **只有 32%** 能正确形式化该 NL 步骤。
  论文据此得出结论：**当前方法在"学生的形式化不对应上下文里提供的 staff solution"这一情形上能力有限**。
- **逐步 vs 整篇的消融**：在带 staff solution 的条件下，**正确证明上两者相当**（tactic 级 56.8 vs 51.8，proof 级 18.0 vs 26.7）；但**错误证明上逐步优于整篇 8%**（30.1 vs 21.9）。论文的理由很实际：**进入导师系统的证明很多是错的**，所以在错误证明上更好是有利的。
- **额外实验**：把**学生的自然语言证明**与 **Lean goal state 信息**放进 autoformalizer 上下文，效果**低于** Baseline + Staff Solution。

## 11. 评估方法

- **三套评估并存，各管一段**：
  1. **Autoformalizer 单独评估**（Table 1）：tactic 级与 proof 级准确率，正确与错误证明分开报；**pass@1**；配 Jeffreys 区间。
  2. **端到端系统评估**（Table 2）：在 **21 条错误证明**上比 Baseline vs LeanTutor 的**生成反馈质量**，四轴 5 分制人工盲评。
  3. **LLM-as-a-judge 的对照评估**（§5.4）：同数据、同轴、用 gpt-4 当裁判，**结论与人工评分相反**。
- **为什么端到端只评"成功 autoformalize"的子集**：论文在 Limitations 里说清楚了——**autoformalization 失败时系统可能给出错误反馈或答不上来**，所以**故意不评那些样本**。这是一个诚实但也是**覆盖缺口**的选择：**它把系统最弱的路径排除在评估之外**（论文自己也承认"我们假设学生证明错即编译器报错，但错误也可能来自 autoformalization，会产生假阳性"）。
- **我们可借用的被动信号**：
  1. **"staff solution 引用率"** 类指标：**模型输出里有多少比例直接来自它拿到的参考材料**（89%），以及**出错时抄参考材料的比例**（51%）。这是**测验"模型是不是在抄上下文"的廉价探针**，对我们的"笔记里的话到底是自己想出来的还是抄教材"这个问题直接对应（见 §12-4）。
  2. **"期望答案不在参考材料里时的正确率"**（32%）——**排除上下文泄漏后的真实能力**，这个数字比总准确率诚实得多。
  3. **Answer Leakage 轴**：一个"越少越好但**不能为零**"的指标——显式给答案本身就是设计目的，所以**指标必须与设计意图一起解释**，否则会把正确的取舍读成回归。
  4. **人工 vs LLM 裁判不一致**：任何"用模型判模型"的结论都必须有一个小规模人工校准，且**不一致时要如实报告**。

## 12. 可迁移机制清单

1. **"忠实性"而非"正确编译"作为质量目标**（论文的核心主张，引 Liu et al. 2025）。编译通过只证明**语法**对；对我们要审的笔记，"**句子读起来通顺**"同理**不构成任何证据**。可直接写成协议里的一句判据。
2. **"表达失败"与"内容错误"必须能被分开**（论文承认它没做到，SAFE 做到了）：任何审查机制的失败通道**不能只有一个**。
3. **逐步 + 逐步编译的纪律**：一次只处理**一个**步骤/断言，且**每一步都立刻做一次确定性检查**（这里是编译），而不是最后一次性检查整篇。理由（论文）：**定位到第一个错误就停**，避免后续错误级联污染判断。
4. **"抄书"是可度量的，而且是主导模式**：89% 的正确 tactic 来自 staff solution；期望答案不在其中时正确率只有 32%。**这条对我们"数学笔记里的中间产物（跟教材抄书）"直接可用**——"这段内容与教材/来源的重叠度"是一个**可计算**的量，而"不重叠时的正确率"才是真实水平。
5. **参考解答作为上下文的价值与风险同时存在**：给参考把 tactic 级从 32.9 提到 56.8（**大幅提升**），但**把模型变成抄写器**（89%），并在错误证明上造成 51% 的抄错。**给参考是双刃剑，必须同时度量"提升"与"依赖"。**
6. **禁列表（循环 + 时序）是一道结构性边界**：不许用当前目标自证（**反循环论证**），不许用"排序在后"的结果（**反时序倒置**）。这两条**零成本、可机检**，且**对笔记审查完全适用**（见 §13、§14）。
7. **"我推不出下一步"是一等结果**：NSG 找不到证明时**上报**而不是编一个。对应我们：**"判不了"必须有输出，不能沉默**。
8. **失败分类的枚举化**：三种反馈（错误识别/提示/显式下一步）+ NSG 的"找不到"。对应我们的"降级原因码"。
9. **反馈的三段式形状**：**定位错误 → 给提示/问题 → 给一条显式但最小的一步**。这是"拒绝时的反馈内容"的一个成熟模板（Danus 的 repair hints 是它的 fact 级版本）。
10. **不泄露答案作为硬约束**（Answer Leakage 轴）：我们的类比是**审查结论不应替代用户的判断**——插件可以指出"这行与来源冲突"，但**不应直接改写用户的数学内容**。
11. **度量要排除上下文泄漏来报**（"期望答案不在 staff solution 里时 32%"）：**任何"我们的机制有效"的声明都应附一个"去掉最强捷径后还剩多少"的数字**。
12. **小库 + 小搜索空间是导师场景的合法特权**：论文把"教师知道解答 + 定理库小"当作**问题变简单的正当前提**，而不是作弊。**我们同样有"用户知道自己在学什么、vault 规模小"这个特权，应当用它换确定性（零 token 的封闭集检查），而不是模仿大库检索。**
13. **人工校准不可省**：LLM-as-judge 与人工评分相反这一发现，是"AI 审查会错"的一手证据；**任何引入模型审查的建议都必须带一条"人工小样本校准"**。
14. **成本纪律**：全部实验 <$4；模型无关框架；不为优化换模型。**先证明机制有用，再谈模型。**

## 13. 与 dsh-math-memory 的映射与差距

| # | LeanTutor 机制 | 我们现状 | 判定 |
|---|---|---|---|
| 1 | 忠实性 > 编译通过 | 无此判据；仓库有"不假装可信"的方向 | **采纳（协议一句判据）** |
| 2 | 表达失败 ≠ 内容错误 | 只有一个 `unverified` 桶 | **采纳**（与 SAFE §14-1 同条） |
| 3 | 逐步 + 逐步检查、第一个错误即停 | 体检按卡，不按句 | **改造**：审查单元下沉到"一句条件断言" |
| 4 | 抄书率可度量；不重叠时才见真水平 | 无重叠度指标；`source` 只记来源不记重叠 | **采纳（重点）**：把"与来源的重叠度"做成可计算探针 |
| 5 | 参考解答双刃剑 | 我们的卡常带 `source`（教材/讲义） | **采纳**：度量要与依赖度一起报 |
| 6 | 禁列表：反自证 + 反时序 | 无 | **采纳（零 token，最便宜的一条）**：`depends_on` 必须指向 card 内更早/别处的内容，且不得自引用 |
| 7 | "推不出"是一等结果 | 体检有清单，但模型侧无"判不了"的显式输出要求 | **采纳**：vault 协议加"判不了必须明说" |
| 8 | 反馈三段式 | ❌ 反馈由用户点，模型修 | **改造**：`needs_review` 应附"错误定位 + 提示 + 最小修正" |
| 9 | Answer Leakage 硬约束 | 插件不改用户内容（既有纪律） | **已一致** |
| 10 | 小库特权换确定性 | 我们 vault 规模小，天然适用 | **采纳（方针）**：用封闭集确定性检查，不模仿大库检索 |
| 11 | 人工校准 | 我们有 ❌/✅ 用户反馈通道 | **已具备同形**，可要求"模型审查结论必须有小样本人工校准" |
| 12 | 成本纪律（<$4） | 我们更严：零 token 优先 | **已一致** |
| — | Lean / LeanInteract / NNG4 / NSG 的 DFS / COPRA / persona 数据构造 / autoformalization 词典 | 无形式化栈、无 tactic 搜索、无训练 | **不适用** |
| — | PeanoBench 式数据集构建 | 我们不做数据集 | **不适用** |

**差距的本质**：LeanTutor 面对的是"**学生的证明**"，它的裁判（Lean）是完备的，所以它的困难全在**把自然语言忠实翻译成形式语言**（这正是它的实验在量的东西）。我们面对的是"**用户和 AI 一起写的数学笔记**"，**没有完备裁判**：我们能做确定性检查的只有**结构与引用**，数学内容本身只有"人对人"的确认。因此 LeanTutor 的可迁移部分集中在**（a）"忠实性"这个目标定义**、**（b）抄书率/脱离参考后的能力这两个探针**、**（c）反自证/反时序的禁列表**，不包括它的形式化栈。

## 14. 行动项

> **[零 token]** = 确定性插件逻辑；**[需模型]** = 需模型参与；**[做不到]** = 本仓库架构下不可行。

1. **[零 token] 禁列两条：反自证 + 反时序。** 体检校验：卡片的 `depends_on`（或 `related`）**不得包含自己**（反循环论证）；若 A 依赖 B，则 **B 的写入时间/`source` 不能晚于 A**（反时序倒置）；违反记 `structural.cyclicOrAnachronistic`。**这两条零成本、可机检，是 LeanTutor 最可直接搬的机制。**
2. **[零 token] "抄书率"探针：与来源的重叠度。** 对每张有 `source` 的卡，计算**卡内句子与来源文本的重叠度**（确定性可做：分词后的 n-gram / Jaccard，仓库已有 tokenize 与 Jaccard 工具用于 duplicate 检测）。产出两个数：**有来源的卡的占比**、**样本卡的平均重叠度**。**依据**：LeanTutor 里 89% 的正确 tactic 直接来自参考材料；**高重叠本身不是错**（跟教材抄书是合法的中间产物），但**它意味着"这条内容没有经过独立验证"**——把这作为**是否值得花力气审查**的排序依据，而不是当作错误。
3. **[零 token] "脱离来源后的正确率"作为审查优先级的输入。** 把"卡的内容**不**在 `source` 里能找到"的那些卡单列一节"**独立产出**"，优先审查它们。依据：LeanTutor 里期望形式化不在 staff solution 时正确率只有 **32%**，是**真实能力**所在处；相应地，**来源之外的内容是最可能出错的地方**。
4. **[零 token] 把"判不了"写成一等输出。** 体检/审查流程必须允许并展示 `unresolved`（判不了）与 `blocked`（依赖未决），**且不得用沉默代替**。依据：NSG 找不到证明时把它上报，而不是编一个下一步。
5. **[零 token] 拒绝时给三段式反馈。** 当卡被标 `needs_review` 时，要求同时写：**定位**（哪一句/哪个前提）→ **提示**（缺什么条件、哪个方向可查）→ **最小修正**（给出可验证的最小改动或一个待查的具体反例方向）。缺任一段就列为结构性不完整。依据：LeanTutor 的三类反馈 + Danus 的 repair hints。
6. **[零 token] `unverified` 的原因码加一档 `ambiguous`。** 与 SAFE 的原因码合并后，`ambiguous` 表示"陈述本身有歧义，先要澄清陈述而不是判真伪"——这正是 LeanTutor 的 autoformalization 失败（表达不了）与我们"内容错"的分界。
7. **[需模型] 把"忠实性"写进 vault 协议的一句话判据。** 建议措辞：「**通顺、读得懂、能编译，都不构成任何证据；只有"给定前文，结论必须成立"被核对过才算。**」依据是 LeanTutor 的 `syntactic correctness is insufficient`。
8. **[需模型] 审查要区分"抄"与"推"。** 模型在 Refine 步或体检跟进时，对每条被审断言要先声明它的**来源关系**：**复述来源 / 改写来源 / 独立于来源**。三档在协议里给出定义，并明确**只有"独立于来源"的断言才需要走完整审查**，其余走"来源是否被正确复述"的轻量核对。依据是 LeanTutor 的 persona 设计（equation-based 与 justification-based 是两种写法而**不是两种内容**）。
9. **[需模型] 人工小样本校准。** 任何"模型审查更准/更省"的结论，必须附一次**小规模人工校准**（样本数可小，但必须 model-blind、必须报告不一致）。依据是 LeanTutor 的 LLM-as-judge 与人工评分**结论相反**的负面发现。
10. **[做不到] 用 Lean 判定笔记数学内容。** 无形式化语料、无 Lean 环境、插件不调模型不联网。
11. **[做不到] NSG 式的"下一步搜索"。** 数学笔记的下一条通常不是可枚举的 tactic；我们也没有形式目标。**不要试图把笔记审查做成证明搜索。**
