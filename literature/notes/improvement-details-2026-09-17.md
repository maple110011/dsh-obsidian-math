## 〇、先认识本系统的六个部位（不然后面看不懂）

这套记忆系统把一切都存成 Obsidian 库里的 markdown 文件。改东西之前要先知道东西在哪：

| 部位 | 在哪里 | 里面是什么 |
|---|---|---|
| **① 记忆卡** | 库的 `.deepseek/memory/records/*.md` | 一张卡记一条可复用的事实/技巧。文件顶部有一段用 `---` 包起来的 YAML 元数据（叫 frontmatter），其中可选一个 `hook:` 小节，用来写"这张卡适合什么类型的问题" |
| **② 检索排序** | 代码 `dsh/preset/note-tools.mjs` | 模型用 `note_recall` 工具做检索。检索用 BM25 词频打分，再叠加一个"这张卡本身可不可信"的加分 |
| **③ 记忆体检** | 代码 `dsh/host/memory-admin.mjs` | 每天一次确定性扫描全部卡片，生成一份报告（强卡/弱卡/没被用过的卡/待重审卡/疑似重复/反模式等），注入到系统提示里让模型处理 |
| **④ 策略卡** | 库的 `.deepseek/memory/strategy/*.md` | 方法层的卡：「遇到什么困难 → 用什么招 → 去检索什么」。有 `status: candidate`（候选）和 `active`（已启用）两种状态 |
| **⑤ 写库协议** | 模板 `dsh/templates/vault-AGENTS.md` | 教模型每轮对话结束时"按需三写"：先追加当天事件卡（episode），再提炼原子记录（record），再局部更新主题/偏好 |
| **⑥ 文献库** | 仓库 `literature/` | 论文卡片 + 研读记录 + 原始全文 |

**"hook 块"到底是什么**（下文会反复用到）：就是记忆卡顶部元数据里的一小节，形如

```yaml
hook:
  operator: probability        # 属于哪个数学分支
  pattern: subsequence_argument # 结构模式
  techniques: [borel-cantelli]  # 用了什么技巧
  applications: 证明 a.s. 收敛类问题
  verified: single-source       # 可信等级：单源 / 互证 / 用户确认
  uses: 3                       # 被检索命中过几次（插件自动写）
  success_rate: 0.67            # 用过之后的成功率（插件自动写）
  last_used: 2026-09-10         # 最后一次用（插件自动写）
  harmed: 0                     # 用过但结果更差的次数（插件自动写）
```

**为什么要发明这个块**：没有它，一张卡只能靠正文文字被搜到；有了它，检索可以按"这属于哪一类问题、用了什么技巧、这张卡可不可信"来加权。它是这套系统最核心的设计。

**当前检索排序的完整公式**（`note-tools.mjs` 第 501–516 行的 `hookPrior` 函数，逐字对应）：

```
可信分 = 0.45 × 成功率
       + 0.25 × 使用次数（除以 10，上限 1）
       + 0.20 × 可信等级（用户确认=1，互证=0.75，单源=0.5）
       + 0.10 × 新鲜度（90 天内线性衰减到 0）

最终得分 = BM25 词频得分 ＋ 可信分 × 权重（占 15%）
```

记住这个公式，**第一项改进就是往它里面加一个因子**。

## 二、最该先做的五项（都不花钱、都不需要调用模型）

> 为什么强调"不需要调用模型"：本项目有一条设计红线——**Obsidian 插件本身不调用任何大模型**。所有"要判断"的事要么由确定性代码做，要么交给正在对话的模型做。下面的方案全部守这条线。

### 第 1 项：给检索加一个「用了它到底有没有变好」的信号

**现在是什么样**

卡片记录了三件事：`uses`（被用过几次）、`success_rate`（成功率）、`harmed`（用过但结果更差的次数）。但**没有任何一个数字回答"用了这张卡，比不用它好多少"**。

问题出在 `uses` 与 `success_rate` 的语义上：这两个数字都来自 `note_recall` 的**命中计数**——也就是"这张卡被检索出来过"，而**不是"这张卡真的帮上了忙"**。

- 一张卡被检索出来 20 次，但其中 18 次模型读了之后判定"不适用"而弃用 ⇒ `uses = 20`，看起来是张热门卡；
- 一张卡只被检索出来 2 次，但两次都直接解决了问题 ⇒ `uses = 2`，看起来是张冷门卡。

在当前的排序公式里，前者因为 `0.25 × 使用次数` 这一项会**排得更靠前**。这是**把"被提到"当成了"有用"**。

**缺什么**

缺一个**带正负号**的净收益量：既要记"用了它、结果好"（正），也要记"用了它、结果差或用户否掉了"（负），然后两个相减。

**为什么要改（外部依据）**

MSCE 这篇论文（arXiv:2607.16621）用这个量做全部治理决策，公式是：

```
增益 = 用了它的那些步骤的平均价值 − 没用它的那些步骤的平均价值
```

并且它做了一个很聪明的处理：**当"没用它"的样本很少时，把这个平均值往一个保守的基线值拉**（它的取值是：基线 0.5，虚拟样本数 5）。举例：如果一张卡只被用过 1 次、成功 1 次，而"没用它"的样本一个都没有，那么增益不会被算成一个虚高的正数，而是被拉向 0.5，也就是"证据不足，先别当回事"。

同族的证据还有两处：GraphMemix 那篇的控制实验里，通用去冗余选择的**净回收是负的**（−6 / −36）；MemForest 那篇里「挑最不相似的一对合并」比随机还差（89.0% vs 91.7%）。**三篇都在警告同一件事：只统计单侧数字（只数好次数）会系统性高估。**

**具体怎么改（建议方案）**

1. 在 hook 块里加一个字段，例如 `gain`（净增益），由插件按上面的公式算出来并写回。**默认不写**（缺失视为"证据不足"，加权时取中性值）。
2. **确定性代理量**：因为我们不能调用模型去给"价值"打分，就用已经存在的事实当代理量。建议只采用下面这两个最没有歧义的：
   - 用户点了「❌ 这张卡有错」⇒ 记负分（这已经在 `harmed` 里了）；
   - 这张卡后来被标成 `superseded`（被新结论取代）⇒ 记负分。
3. **把它接进排序**：在 `hookPrior` 的公式里，让 `gain` 占一份权重。建议第一版**不要加大总权重**，而是从现有的 `0.25 × 使用次数` 里分一部分出来（例如改成 `0.15 × 使用次数 + 0.10 × 净增益`），这样排序的总量级不变，改动可回退、可对比。
4. **小样本收缩**：照抄"基线 0.5、虚拟样本数 5"的做法，让"只被用过一两次"的卡不被高估。

**改哪里**

| 文件 | 改什么 |
|---|---|
| `dsh/preset/math-memory.mjs` | 体检回写统计的地方（现有 `uses` / `last_used` 的回写函数在 988–1120 行附近），加 `gain` 的计算与写回 |
| `dsh/host/memory-admin.mjs` | 同名函数（这个仓库有两份实现，改一份必须改另一份，见 AGENTS.md 第 3.3 条） |
| `dsh/preset/note-tools.mjs` | 第 501–516 行 `hookPrior` 的公式 |
| `dsh/templates/records-readme.md` | 字段说明（告诉模型这个字段由插件维护、它不许手写） |

**怎么算改对了**

- `scripts/test-memory.mjs` 加断言：① 样本为 0 时不产生虚假增益；② 只有 1 次好评时增益被拉向中性值而不是接近满分；③ 用户点过「❌」之后，同一张卡的净增益为负。
- 按 AGENTS.md 第 6 条做**变异验证**：故意把收缩逻辑删掉 ⇒ 断言必须报错 ⇒ 恢复 ⇒ `git diff` 为空。

**注意**

- 必须先想清"负分从哪来"。目前唯一确定的负信号是用户点 ❌（`harmed` 累加）和卡被标 `superseded`。**不要**拿"用户继续追问"当负信号——追问也可能只是想知道更多，会引入噪音。
- 改完**必须重建 `main.js`**（AGENTS.md 第 3 条第 1 款），否则 CI 的字节级门禁会红。

### 第 2 项：记录"谁依赖谁"，并在依赖的东西失效时列出待复查清单

**现在是什么样**

卡片之间有 `related: []`（相关链接）和反向链接。但 `related` 是**双向、无方向**的：A 的 `related` 里有 B，B 的 `related` 里也有 A。系统**不知道**"B 是在 A 的基础上推出来的"还是"B 只是和 A 主题相近"。

后果是很实际的一个场景：假设你先记了一张卡「定理甲」，后来又用它做了两张笔记、写了三张问题模板卡。半年后你发现「定理甲」记错了，把它标成 `superseded`。**系统不会告诉你"那两张笔记和三个模板卡是建立在它上面的，需要复查"**——它们会继续以"仍然有效"的姿态出现在检索和体检里。

**缺什么**

缺两样：
1. **有方向的依赖关系**（"这张卡依赖哪些卡"，与"相关"分开记）；
2. **失效传播**（某卡失效时，体检列出所有下游待复查清单）。

**为什么要改（外部依据）**

这一项是**三篇独立来源指向同一处**，是这批材料里最集中的共识：

- **Danus**（arXiv:2607.06447，北大 FrenzyMath 的数学推理编排系统）：它的记忆叫"事实图"，每条已验证事实**连同依赖它的入边一起保存**，而且事实是**内容寻址、可级联撤销**的——撤销一条，依赖它的东西全部被牵出来。
- **MemForest**（arXiv:2609.08273）：它宁可先合并"度数低"的节点、把"度数高"的枢纽节点留到最后，理由原文是"高度数节点通常是事件的核心，携带更多核心信息，不应被过早合并"。**度数**就是"有多少东西连着它"。
- **MSCE**（arXiv:2607.16621）：它要求每个技能都带"证据锚点"，并明确写"高层记忆存证据 id 而不是复制原始观测"，这样"这条技能凭什么可信"可以一键回溯。

**具体怎么改（建议方案）**

1. 在记录卡的元数据里加一个字段，例如 `depends_on: [rec-xxx, rec-yyy]`，**只记方向**：本卡是在这些卡的基础上成立的。
2. **只让模型填，插件只读**（符合现有分工：内容字段模型维护，统计字段插件维护）。
3. 体检里加一段确定性逻辑：凡是本卡被标成 `superseded`、或被标 `needs_review`、或可信等级被降级 ⇒ 找出所有 `depends_on` 指向它的卡 ⇒ 输出"下游待复查清单"。
4. 输出格式照现有体检的写法（它已经会把待重审、疑似重复等分节列出来），不要发明新格式。

**改哪里**

| 文件 | 改什么 |
|---|---|
| `dsh/templates/records-readme.md` | 卡片模板加 `depends_on` 字段与填写规则 |
| `dsh/templates/theorems-readme.md`、`templates-readme.md` | 同上（定理卡与问题模板卡也会被依赖） |
| `dsh/host/memory-admin.mjs` | 体检里加"下游待复查"分节 |
| `dsh/templates/vault-AGENTS.md` | 体检响应那一节加一条：遇到"下游待复查"怎么处理 |

**怎么算改对了**

- `test-memory.mjs` 构造 A ← B ← C 的依赖链，把 A 标 `superseded` ⇒ 断言体检输出的清单里**同时**有 B 和 C。
- 再构造一个"只有 `related` 没有 `depends_on`"的对照组 ⇒ 断言它们**不**被列进清单（防止把"相关"误当"依赖"，那会让清单爆炸）。

**注意**

- 这个字段会让模型多写一点东西，**初期建议只对"定理卡/问题模板卡/策略卡"要求填，普通事实卡可选**，否则会显著增加每轮的写入负担。
- 它和第一项有协同：级联列出的"下游卡"正是"净增益为负"最可能的来源。

### 第 3 项：把「哪些卡被自己的适用边界拦下了」从纯文字改成结构化数据（**这是对我上一版错误的更正**）

**现在是什么样（重新核实过）**

适用边界 `not_applicable_when` 的机制**已经完整实现**：

- 卡上写一句边界（如 `not_applicable_when: 成本非二次、μ 非绝对连续`）——文档要求写成**短句/关键词列表、每条不超过 12 字**，因为要拿去做精确匹配；
- 检索时，如果查询里出现了边界里的短语，这张卡**不进候选**，而是被放进一个单独的 `excluded` 列表，并注明"命中了哪条边界"；
- 给模型的提示里明确写"另有 N 条因**适用边界**被排除（不是"没找到"）"——这个措辞很重要，否则模型会以为库里没有。

测试也到位（`test-memory.mjs` 第 1490–1502、1676 行）。

**那还有什么可改的**

两个小问题：

1. **文档没有说明这件事有多重要。** 现在文档的口气是"强烈建议写"。但 MSCE 的消融实验给出了硬证据：把"适用性过滤"这一环拿掉、直接把检索到的技能注入，**在它测试的每个领域都掉分、而且成本都上升**。也就是说，**这不是"锦上添花的优化"，而是"防止帮倒忙的保险"**。文档应当据此改口径。
2. **"有多少卡是因为边界被拦下"这个数字没人统计。** 这是一个很有用的健康指标：
   - 如果长期是 0，说明要么边界写得太少，要么没人写到点子上；
   - 如果某些卡的边界**频繁**命中，说明这张卡的适用面可能被写得过窄，或者查询的表达方式有问题。

**改哪里**

| 文件 | 改什么 |
|---|---|
| `dsh/templates/records-readme.md`、`strategy-readme.md`、`vault-AGENTS.md` | 把"强烈建议写"改成"这是防止帮倒忙的机制"，并附上依据（一句话即可，不必引用论文全文） |
| `dsh/preset/note-tools.mjs` | 在检索统计里给"因边界被排除"单独计数（写进 `cache/retrieval-stats.json`） |
| `dsh/host/memory-admin.mjs` | 体检报告里加一行"边界拦截统计" |

**怎么算改对了**

- `test-memory.mjs` 加断言：一次查询里若某卡被边界拦下，统计文件里该项计数 +1；同一张卡被拦下不重复计数（按卡去重），否则一次失败的检索会把它刷爆。
- 文档改动无需测试，但要跑 `check-doc-consistency.mjs`。

### 第 4 项：让"状态"真正等于"权限"

**现在是什么样**

系统里已经有一堆状态字段，但**它们目前的主要作用是"显示"和"体检分类"，而不是"禁止使用"**：

| 状态字段 | 取值 | 现在谁在看它 |
|---|---|---|
| 策略卡 `status` | `candidate` / `active` | 体检会把候选卡按"用过≥3次且成功率≥0.6"提升为 active；检索时**候选卡照样能被检索到并当作依据** |
| 记忆卡 `status` | `active` / `superseded` | `superseded` 的卡**已被排除**出检索（这条已经做对了） |
| 备忘 `status` | `inbox` / `polishing` / `done` | 只用于提醒与展示 |
| 可信等级 `verified` | `single-source` / `cross-referenced` / `user-confirmed` | 参与排序加权（0.5 / 0.75 / 1） |

所以唯一真正做到了"状态即权限"的是 `superseded`。**策略卡是明显的缺口**：文档自己都说"策略卡是「候选」不是「指令」"，但代码层面**没有任何东西阻止**一张 `candidate` 卡被检索出来、被模型当成结论依据用。

**缺什么**

缺"**没达到某个状态，就结构性不能做某件事**"的硬规则。

**为什么要改（外部依据）**

VeryMath 的 Co-Mathematician 项目（github.com/VeryMath/co-mathematician）有一条写得很硬的规则：

> 草稿目标不可执行。目标只有在 `status: approved` 时才能接收工作流。

而且它有对应的命令 `co-math check-gate --gate goal_approval`——**这条规则是可被程序检查的**，不是提示词里的一句劝告。

同一组织下的 Danus 把这件事做到了极端：它的权限**由工具表强制**而不是靠提示词——主 agent 的工具列表里**根本没有**"提交事实"这个工具，所以"负责指挥搜索的 agent 在结构上无法把未验证的数学引入事实库"；验证器则**连写权限都没有**。原文说得很清楚：**"权限由 MCP 角色表强制，不是靠提示词"**。

**具体怎么改（建议方案）**

1. **策略卡**：`candidate` 状态的卡仍可被检索（它是有价值的线索，不该藏起来），但**输出时必须与 `active` 卡分开**，并在提示里标明"以下为**候选**线索，尚未验证，不得直接作为结论依据"。这与现有"被边界排除的卡单独列出"是同一种做法，可以直接照它的实现写。
2. **备忘**：`done` 状态的条目不再计入"活跃备忘"提醒。
3. 把这三条硬规则写进 `vault-AGENTS.md`，并在 `test-memory.mjs` 里各加一条断言。

**改哪里**

| 文件 | 改什么 |
|---|---|
| `dsh/preset/note-tools.mjs` | `note_recall` / `note_strategy` 的输出分组（照第 786–828 行 excluded 的写法） |
| `dsh/templates/strategy-readme.md`、`vault-AGENTS.md` | 硬规则文本 |
| `dsh/host/memory-admin.mjs` | 体检里"候选卡仍未被验证"的统计 |

**怎么算改对了**

- 构造一张 `candidate` 策略卡 + 一个能命中它的查询 ⇒ 断言它出现在"候选线索"分组里、**不**出现在正常结果里。
- 变异验证：把分组逻辑去掉 ⇒ 断言必须失败。

### 第 5 项：把"只有插件能改这些字段"写成明文契约

**现在是什么样**

插件会往卡片里回写四个数字：`uses`（用了几次）、`last_used`（最后使用日期）、`success_rate`（成功率）、`harmed`（用过但结果更差的次数），以及升级凭据 `verified_by`。文档（`records-readme.md` 第 58–60 行）已经明确告诉模型"**你永远不手写/手改这四个字段**"。

**而且已经有一道防线**：体检里有"**越权升级**"检测——如果一张卡的 `verified` 等级高于 `single-source`，却没有 `verified_by` 凭据，就会被列为越权升级并要求重判（`memory-admin.mjs` 第 1337、1370 行的 `unjustifiedUpgrade`）。

**那还缺什么**

三个缺口，都不大但都是真的：

1. **契约只写在给模型的文档里，没写进"设计规格"。** `docs/memory/design.md` 是描述"代码里真实存在什么"的地方，但它没有明确说"这四个字段的唯一写入者是插件、模型只能提案"。新人（或未来的 agent）读设计文档时会以为这些字段是普通内容字段。
2. **检测只覆盖 `verified` 等级，不覆盖四个统计数字。** 如果有人（模型或用户手改）把 `uses` 从 3 手改成 30，现有的 `usesMismatch` 检查能抓到"声明值与合并值不一致"（第 1615–1616 行），但它报的是"不一致"，**没有把它定性成"越权修改"**。两者应该合并成同一类违规。
3. **没有"增量回执"的固定格式。** 插件做了一堆确定性维护（回写统计、归档旧事件、更新索引），但**报告给模型和用户的形式是散文**。VeryMath 的做法值得抄：它的脚本只回增量，且用固定符号——
   - `+` 表示新建，`~` 表示更新，`!` 表示检测到冲突，`⚠` 表示超期；
   - **没有变更就什么都不输出**。

   这带来的好处很具体：模型不需要读全量数据就知道"刚才系统改了什么"，而且"没有变更"本身是一个明确信号（现在模型看到一段没变化的报告，无法区分"没变"和"没看懂"）。

**改哪里**

| 文件 | 改什么 |
|---|---|
| `docs/memory/design.md` | 新增一小节：字段所有权表——哪些字段模型可写、哪些只有插件可写、越权怎么被发现 |
| `dsh/host/memory-admin.mjs` | 把"统计字段声明值与合并值不一致"归类进"越权修改"，与 `unjustifiedUpgrade` 并列 |
| `dsh/preset/math-memory.mjs` | 体检报告的增量回执格式（固定符号） |
| `dsh/templates/vault-AGENTS.md` | 告诉模型如何解读这四个符号 |

**怎么算改对了**

- `test-memory.mjs` 构造"模型把 `uses` 改成 30"的场景 ⇒ 断言体检把它报成越权修改（而不只是"数字不一致"）。
- 断言"无变更时不输出任何增量行"。

**注意**

- 改回执格式会同时影响**给模型看的系统提示**和**给人看的报告**，属于用户可见变化 ⇒ 按 AGENTS.md 第 5 条要写进 `CHANGELOG.md` 的 `[Unreleased]`（**不要**自己改版本号）。
- 若触及 `dsh/**` 与模板 ⇒ 必须重建 `main.js`。

## 三、第二批：需要一点设计，但收益明确

### 第 6 项：统计"同一个招数被几个不同场合独立验证过"

**现在是什么样**：体检会报"疑似重复"的卡，但没有统计"同一个招数在不同时间、不同题上出现过几次"。

**为什么要改**：MSCE 里有一条我认为很关键的规则——它**只有当同一个模式被至少 2 个不同的事件（不同次的交互）支撑时，才允许归纳出一条策略**，原文理由是"防止一条长轨迹自己撑出一个过于专用的策略"。

这条规则的用处是**区分"一次巧合"与"真的可复用"**。我们现在判断一个招数好不好，靠的是 `success_rate`，但那个数字来自"被检索命中"，**不区分这 3 次命中是同一道题反复出现，还是三道不同的题**。

**怎么做**：用"同一个主题（`topic` 字段）+ 事件日期接近（例如前后 3 天内）"作为"同一个场合"的判定，统计同一个"困难 × 招数"组合覆盖了几个不同场合。数据都已经在库里：事件卡有日期，记录卡有 `topic`。

**依据的巧合**：MemForest 也用"语义相近 + 时间相邻"来划分"同一个事件"，而且它给的权重是**语义 0.8、时间 0.2**——也就是说时间只做辅助。这个比例可以借鉴。

**改哪里**：`dsh/host/memory-admin.mjs`（体检里加统计）、`docs/memory/design.md`（记录这条判据）。

**怎么算改对了**：构造"两个不同日期、同主题"的事件 ⇒ 断言场合计数为 2；"同一天、同主题" ⇒ 计数为 1。

---

### 第 7 项：策略卡升级要过三道门，而不是一道

**现在是什么样**：策略卡从 `candidate` 升到 `active` 的条件是 `uses ≥ 3 且 success_rate ≥ 0.6`（`memory-admin.mjs` 的 `PROMOTE_USES` / `PROMOTE_RATE`）。

**缺少什么**：MSCE 的技能晋级有两道门 + 三道校验，我们可以补上其中纯确定性的部分：

| 门 | 它做什么 | 我们能不能做 |
|---|---|---|
| **增益门** | "用了比不用好" | 能做（第 1 项做完就有了） |
| **稳定性门** | 近期证据应当吻合当前的做法描述，而不是迫使大改写 | 能做：统计这张卡被改写过几次；反复改写说明它还没定型 |
| **接地校验** | 卡片声称用的定理/技巧，必须真的在它引用的证据里出现过 | **能做，而且这是纯确定性的、最容易做的** |
| schema 校验 | 必填字段齐全 | 我们已有结构校验 |
| 覆盖测试 | 不发明无支撑的命令 | 对应我们的"不编造"纪律，可归入接地校验 |

**为什么"接地校验"最该先做**：MSCE 里"引用的证据必须来自支持集"是**插入前的最后一道确定性检查**，不合格就**丢弃草案**而不是发布。我们现在的问题很具体：策略卡有 `provenance`（出处）字段，但它是**一段文字**，不是结构化的列表。所以"这张卡说它用了『Borel-Cantelli』，但证据里的三张卡都没有这个技巧"这种问题，**现在没有任何东西能发现**。

**改哪里**：`dsh/templates/strategy-readme.md`（把 `provenance` 升级为结构化列表 + 声明用到的定理/技巧）、`dsh/host/memory-admin.mjs`（体检里加"未接地策略"清单）。

**怎么算改对了**：构造一张声称用到"技巧X"、但引用的证据卡里没有"技巧X"的策略卡 ⇒ 断言体检把它列进"未接地策略"。

**顺带补一个字段**：MSCE 的技能有"触发条件"和"前置条件"两样，我们现在只有负向的 `not_applicable_when`（什么时候**别**用）。建议补一个**正向**的前置条件字段（"要能用这条，先得有什么"）。注意两者的行为要不同：负向边界是**硬拦截**，正向前置条件应该是**降权**而不是拦截（否则缺一个前置条件就完全搜不到，太粗暴）。

### 第 8 项：用户说"不对"的时候，除了改成功率，还要收窄边界

**现在是什么样**：用户点「❌ 这张卡有错」之后，插件会（`memory-admin.mjs` 第 214–266 行附近）：

- 把 `success_rate` 封顶、把可信等级降一级、标上 `needs_review: true`、累加 `harmed`。

**缺什么**：MSCE 在这套动作之外还做了一件事——**收窄适用边界**（它叫 `shrink`）：用户否决意味着"在这种场合下这张卡不适用"，那就应该把那个场合的特征**追加进边界描述**，让它以后自动被拦住。

这个动作的性价比很高：我们现在 ❌ 之后卡还在库里、下次遇到同类问题它**还是会被检索出来**（只是权重低一点），因为边界没有变。加一句边界就变成"直接被拦下，并在 excluded 里说明原因"——用户能立刻看到系统学到了。

**另外一件**：MSCE 把失败经验组织成**成对的对比指导**——形如（上下文、该做的、该避免的、证据、可靠度）。我们现在的"反模式"是一句话散在卡的技巧列表里，**没有结构、也没链到具体卡片**。建议在策略卡里加一对字段：`prefer: []`（建议这么做）与 `avoid: []`（避免这么做），各带证据链接。

**改哪里**：`dsh/host/memory-admin.mjs`（❌ 的处理路径）、`dsh/templates/strategy-readme.md` / `records-readme.md`（新字段）、`dsh/preset/note-tools.mjs`（新字段参与排序，可选）。

**怎么算改对了**：构造一次 ❌ ⇒ 断言该卡的 `not_applicable_when` 确实变长、并且此后用那个场合的特征去检索时**该卡被拦截**。

**注意**：收窄的短语必须符合现有约束（**短句、每条不超过 12 字**），否则会把边界写成散文，而边界是靠精确匹配工作的——写成散文会被切成碎片，门控就不准。这是文档里已经写明的坑。

### 第 9 项：把"检索有多费劲"和"花了多少代价"也量出来

**现在是什么样**：我们的引擎探针（`scripts/qa/engine-probe.mjs`，零花费、可随意跑）目前报告的是"能不能召回到目标卡片"，以及之前已落地的"可达性分层"和"净回收"。

**缺什么**：三个指标。

1. **平均检索轮数**：为了取到足够信息，平均要检索几次。MemForest 用了这个指标（它叫 `Avg-R`），并且证明自己的方法把轮数从 3.10 降到约 2.6。这个指标直接反映**检索结果的信息密度**——命中了但还得再搜三次才凑够，和一次就够，用户体验完全不同，但命中率看不出来。
2. **代价与效果必须并看**：MSCE 论文自己声明，它的成本指标"应当与准确率合看，因为低成本可能来自提前终止或工具使用不足"。只报命中率、不报代价，会奖励"草草结束"。
3. **在高重复度与低重复度两种库上各测一次**：MemForest 的做法很值得学——它同一个压缩方法在 Mem0（低冗余文本）和 M3-Agent（高冗余多模态）两个宿主上各测，从而给出**适用边界**而不只是一个分数。我们可类比为"笔记为主、记忆少"与"记忆密、重复多"两种库。

**改哪里**：`scripts/qa/engine-probe.mjs`、`scripts/qa/cases.json`、`docs/memory/testing.md`（方法论说明）。

**怎么算改对了**：探针输出新增这三类数字，且**零花费**（不进 CI 的联网部分务必不要跑；AGENTS.md 第 4 条要求先问你）。

**建议**：这三项与已有的"可达性分层/净回收"是同一族指标，**合成一次探针升级**比分成四次改动更好，避免探针接口反复变动。

### 第 10 项：文献库的状态提醒与来源登记

**现在是什么样**：文献库里每张卡有 `status`（`unread` / `reading` / `distilled` / `archived`）。但存在一个**已知现象**（`docs/literature.md` 第 152 行自己承认）：`.index.json` 和 `index.md` 里的状态是导入器写的机器默认值（恒为 `unread`），**和卡片里人工维护的状态可能不一致**。所以索引里看不出真实进度，也没有"这张卡放了三个月没读"的提醒。

**怎么改**（抄 VeryMath 文献库的做法）：

1. **陈旧提醒**：`unread` 超过 N 天、`reading` 超过 M 天就列出来。它用的是"捕获时 7 天未读提醒、精读中超过 30 天提醒"，并给四个处置选项（继续 / 降级 / 归档补笔记 / 确认放弃）。
2. **来源登记规范化**：VeryMath 的 OptSkills 包有一个 `SOURCES.md`，记**上游仓库 + 快照 commit + 明确排除项**（例如"只搬产物，不搬训练管线"）。我们的 `library.bib` 记录书目信息、`.raw/<key>/meta.json` 记文件校验和，但**对"从外部引入的机制/结论"没有登记惯例**——目前只用超链接。补上"来源 + 版本/快照 + 明确不采纳的部分"，可以防止"二手印象被当成事实入库"。本次调研里 OptSkills 就踩到了：arXiv 摘要页抓取失败，卡片里必须显式标注"摘要为改写，非原文"。
3. **（可选）定理级引用**：VeryMath 用稳定的编号式引用（形如 `paper:arxiv:2101.00001#Lem-3.1`），并**明令禁止**用中文句子当链接（他们禁止 `[[本文 Lemma 3.1 笔记]]`）。我们的 `citekey` 已经做到了"文献级"的唯一编号；要不要细到"定理级"，成本是给定理卡引入一套新编号规则和校验，**这一项建议你决定是否值得**。

**改哪里**：`docs/literature.md`（流程）、`literature/index.md` 的状态语义、必要时 `scripts/lit-import.mjs`。

## 四、第三批：要动代码或动检索核心，建议和检索重构一起评

### 第 11 项：注入预算做成可选档位

**现在是什么样**：系统提示里每类记忆能占多少字符是**代码里的固定常量**（`docs/memory/design.md` 第 54–67 行有完整表格）：个人偏好 4000 字符、主题索引 1800、记录索引 800、问题模板索引 600、事件索引 1200、备忘摘要 1200、跨会话问答线索最多 6 组 / 3000 字符、体检报告 1200、工作草稿 500。

**为什么要改**：MemForest 把压缩率做成一个滑钮（30% / 50% / 70%），用户按需要选。我们的预算是一个隐藏常量，用户既看不到也调不了——但它直接决定"模型每次开机看到多少记忆"，和侧栏卡顿、上下文窗口都有关。

**建议**：做成"精简 / 标准 / 富上下文"三档。

**注意**：要动 Obsidian 设置页 ⇒ 必须重建 `main.js`；若新增环境变量，`docs/env-vars.md` 是唯一参考且由 `check-env-vars.mjs` 做代码与文档的双向一致校验。

### 第 12 项：检索改成"分层 + 失败回退"

**现在是什么样**：`note_recall` 是**一次统一的 BM25 排序**（笔记 + 全部记忆层一起排），另有 `note_strategy` 走方法层。没有"先试 A，A 不行再退到 B"的显式链条。

**MSCE 的做法**是三层级联：① 先匹配"技能"（≈我们的策略卡）；② 同时命中"环境认知"时，环境认知**只提供参数和边界解释，不覆盖技能的做法**；③ **技能没命中、或技能失败了，就退回证据层**（≈我们的事件卡与记录卡）。

**建议**：**先只补协议文本**——在 `vault-AGENTS.md` 第 5 节写明"策略卡命中但执行失败 ⇒ 回退 `note_recall` 读记录卡与事件卡"。改检索核心属于检索重构（`docs/memory/retrieval-v3.md`）的地盘，**不要单独动**，否则会和那条线的实验结论打架。

## 五、明确不做的事（附理由，防止以后有人重复提议）

| 不做 | 理由（大白话） |
|---|---|
| **自动合并内容重复的卡片** | MemForest 的核心是"把相似的记忆合并成一条"，效果确实好，但：① 合并要用大模型改写文本 ⇒ 违反"插件不调模型"红线；② **合并是不可逆的**，原始措辞没了，而我们整个设计的立足点是"可溯源、可纠错"（冲突时标 `superseded` 而不是删除）；③ 我们的量级远小于它的 6000 条记忆，收益小。**但它的排序判据要采纳**（见第 13 项） |
| **改用 JSON 或 SQLite 当事实源** | 我们的状态就是 Obsidian 库里的 markdown 文件，这不是妥协而是特性：用户能直接读、能直接改、Obsidian 能原生编辑、grep 能用。VeryMath 选 JSON 是它的场景选择 |
| **多智能体蜂群 + 并行证明搜索** | 那是研究级系统（Danus）的东西；我们是给个人做数学学习辅助。而且它的运行姿态是"关掉全部审批和沙箱"（它自己的文档警告要在隔离主机上跑），**与本项目 fail-closed 的安全姿态正好相反** |
| **把技能装进 agent 的全局技能目录让它自动发现** | 会扩大工具面，破坏我们"最小工具面 + 从不自动提权"的设计 |
| **用大模型做那五个判断**（给反思打分、把用户反馈量化成分数、归纳策略、抽象环境认知、起草技能） | 全部违反"插件不调模型"。**只取它的确定性判定骨架**（必填字段校验、证据接地、阈值比较） |
| **按时间邻域做检索** | MemForest 这么做是因为它的对象是连续对话和视频片段，"时间上挨着"约等于"内容相关"。我们的对象是数学笔记，**同一天读的两篇无关论文不该互相带出来** |
| **照搬 Co-Mathematician 的整套重流程** | 目标要审批、工作流分四类、报告要过评审才能出终稿——对即时学习对话太重。**只抄"状态 = 权限"这个轻量形状**（第 4 项） |

## 六、还有一项我没在上面单列，但它其实最该早做

### 第 13 项：体检报"疑似重复"时要给出顺序依据，并保护枢纽卡

**现在是什么样**：体检会列出疑似重复的卡片，**但没有排序依据**，也没考虑"这张卡被很多别的东西引用"。

**为什么要改**：MemForest 有一组很有说服力的对照实验：

- 它证明了**合并优于剪枝**（压缩超过 50% 后，删减类方法明显掉分，合并类还能撑住）；
- 更关键的是它做了一个反向对照：**"挑最不相似的一对合并"（89.0%）比"随机挑一对合并"（91.7%）还差**，而它自己的做法（挑最相似的一对）是 96.0%。

结论很直接：**这个动作的价值全在"挑哪一对"，挑错比不做更糟。** 而且它给了理论依据：合并两个越相似的节点，合并后与查询的相似度下界越高（公式 `s_l ≥ s_i − (1−λ)·√(2 − 2ρ)`，其中 ρ 是两个节点的相似度）——ρ 越大，下界越高，也就是"越不容易把有用的东西合没了"。

同时它有一个明确的保护规则：**在树里度数高的节点是枢纽，携带核心信息，不应该被过早合并**（它把这写进边权公式：`w' = 0.99·w − 0.01·(两端度数之和)`）。

**对我们的具体做法**：

1. 疑似重复清单**按相似度从高到低排序**（先处理最像的一对）；
2. 计算每张卡的**反向链接数**（`note_links` 工具已经有这个数据，零成本），作为"结构枢纽度"；
3. 枢纽卡（被很多卡引用的）在清单里**单独标出并排除**出"建议合并"——因为一旦它被改写或标 `superseded`，影响面最大（这一点正好和第 2 项的依赖级联是同一个道理）。

**改哪里**：`dsh/host/memory-admin.mjs` 的体检输出。

**怎么算改对了**：构造"A 与 B 互相链接、C 是孤立的重复卡"⇒ 断言 C 先被建议合并、A 与 B 被标为枢纽。

## 八、需要你拍板的四件事

1. **净增益的"负分"从哪里来？** 我建议第一版只用两个最确定的信号：用户点过「❌」、卡片被标 `superseded`。**不要把"用户继续追问"当负分**（追问可能只是想知道更多）。你如果有别的偏好信号，现在定比以后改便宜。
2. **探针指标升级一次做完还是分批？** 一次做完信息量最大，但要动探针接口、改动面大；分批则每批都能独立验证。
3. **注入预算档位值不值得做？** 它要动 Obsidian 设置页并重建 `main.js`，若新增环境变量还要同步 `docs/env-vars.md`（有双向一致校验守卫）。
4. **文献引用要不要细到"定理级"？** 收益是精确引用到某条引理；成本是给定理卡引入新编号契约与校验。
