# agent 仓库维护经验（通用清单）

> 本文是**通用**方法，不是某个仓库的说明书。素材来自一次真实的可维护性审查与整改（面向「能否长期交给 AI agent 维护」的视角）。凡引用具体仓库的地方都只作为**例证**，抽象出来的判据可套用到任何代码仓库。
>
> 目标读者：① 想让 AI agent 长期参与维护的仓库维护者；② 被派去维护某个仓库的 agent 自己。

---

## 0. 一句话结论

**给 agent 的仓库，瓶颈从来不是「代码写得漂不漂亮」，而是三件事：**

1. **入口**——agent 冷启动时能不能在三十秒内知道「这是什么仓库、改哪里、怎么验证」；
2. **验证信号**——它跑的命令输出的是**可信的**真假，还是**随环境变化**的红绿；
3. **真相源**——同一个事实是否只有一处；若有 N 处，N 处是否**互相守卫**。

人类维护者可以靠记忆、直觉和「问同事」绕过这三件事；agent 不能。它只有文件、命令输出和这次对话。**所以对 agent 的可维护性 ≈ 仓库的「可被独立证据驱动」程度。**

一个反直觉的推论：**纪律齐全的仓库也可能对 agent 极不友好**。CI 双平台、版本五处一致、字节级重建门禁、几百项回归测试都到位，agent 依然可能一事无成——只要它跑的那条命令在它的环境里必红，而且红得和真回归一模一样。

---

## 1. 第一原则：验证信号必须可信

这是全部经验里最重要的一条。agent 的工作闭环是「改 → 跑 → 看反馈 → 再改」。反馈不可信，闭环就断了：它要么把正确的代码改坏，要么声称修好了但没修。

### 1.1 假失败比没有测试更糟

**没有测试**时，agent 知道自己不知道。**假失败**时，agent 会去找一个不存在的 bug，并且**很可能改坏本来正确的东西**。

最危险的形态是「**守卫把「没跑起来」当成「结果错了」**」：

- 某守卫会真跑各测试套件、解析它们的计数行，再和文档里的数字比对。在禁止子进程管道 stdio 的环境里，子进程 `spawn` 直接失败、输出为空，守卫把计数读成 **0**，于是报出 **18 条「文档漂移：文档写 232、实际 0」**——而文档全是对的。
- 一个听话的 agent 会去「修」这些文档。**它会把 18 个正确的数字改成 0。**

**判据**：任何「跑子进程 → 解析输出」的守卫，都必须能区分三种状态：**真拿到了结果** / **这个套件按设计跳过** / **子进程根本没起来**。第三种绝不能与前两种混同。前两种可以比较，第三种只能报告。

### 1.2 `cmd1 && cmd2 && …` 是信息毁灭器

一条 `&&` 链在第一个失败处停下。如果第一个失败是**环境性**的（比如本机没有某个依赖、子进程被禁止），后面每一条命令都**从未运行**——而输出只有「失败」。

- 实测：一条 25 条命令的 `&&` 链在第 5 条断掉，**其后 16 条从未执行**。于是「测试失败」这个信息量约等于零：既不知道有几条真的坏了，也不知道哪些根本没跑。

**判据**：门禁入口应当是**汇总器**——跑完所有项、逐项报告状态、最后汇总；失败项附上该命令输出的末尾。并提供一个「只跑匹配项」的开关，让 agent 能低成本迭代单点。

### 1.3 计数必须自数，不能自报

如果测试套件打印的分母是**手写常量**，那么「全绿」只是**算术**，不是覆盖证据；一旦有人加了断言忘了改常量，分母就永久性地撒谎。

- 实测：一个套件写死 `EXPECTED_CHECKS = 31` 而实际执行 **32** 个断言；另一个打印 `7 - failed`/`7` 而可达断言是 **8** 个（9 个调用点里有一个在 else 分支）。
- 更糟的是：**文档的数字锚点盯着这些自报数**，于是错数字被抄进了 5 处文档。错误从「一个常量」扩散成「跨文件的共识」。

**判据**：分母由断言函数自己累加（`total += 1`），末尾打印真实值。

### 1.4 环境限制要显式降级，不能伪装成失败

某些测试在开发机上不可能跑（需要真实服务、真实凭据、真实桌面、子进程权限）。**正确做法不是删掉它，而是让它声明「我在这个环境里跑不了」并给出确切原因**，同时**仍然执行它能在本机执行的那部分检查**。

- 实测（面板鉴权 E2E）：环境禁止子进程写宿主状态文件。改造后它在无法启动子进程时输出 `SKIP` 并打印**确切的失败路径**（`EPERM … open 'C:\Users\…\cordis.yml'`），退出码 0；而在能跑的环境里照旧断言。
- 关键配套：**门禁汇总器要把「子进程没起来」单独标成环境结果**，否则 SKIP 只是把问题藏起来。

**判据**：一个测试的状态有四种——**通过 / 失败 / 按设计跳过（附带原因）/ 环境不可用（附带证据）**。把这四种压成「红/绿」两种，就是在制造假失败。

### 1.5 守卫必须被证明「会失败」

一个从没失败过的守卫，和没有守卫的区别是**不可知**的。所以每加一条守卫，都要做**变异验证**：

> 故意制造这条守卫声称要抓的缺陷 → 确认它确实报错 → 恢复现场 → 确认恢复（哈希/`git diff` 为空）。

这一步花的时间很少，收益是**把「我以为它管用」变成「我知道它管用」**——而且它会抓出守卫本身的设计缺陷。

- 实测收益：一条安全守卫在变异验证时暴露了「我修的那一半不是漏洞的那一半」；一条一致性守卫在自测时抓出了自己的提取器 bug（参数默认值里的 `{}` 提前结束了作用域）。

**判据**：验收标准不是「跑了没报错」，而是「**它在该报错时确实报错**」。验收报告里要能附上那句报错。

## 2. 入口：agent 冷启动需要什么

agent 开新会话时**没有记忆**。它拿到的只有：仓库文件、它能跑的命令、以及被自动注入的少数文件。

### 2.1 必须有一个「三十秒入口」

放在仓库根、会被自动发现的位置（如 `AGENTS.md` / `CLAUDE.md` 之类约定文件），内容应当是：

1. **这是什么仓库**——有几个产物、彼此什么关系、谁消费谁（❌ 不要写愿景，要写数据流）；
2. **文件地图**——「改 X → 必须同时做 Y」的对照表（✅ 这是最有价值的一节）；
3. **铁律**——几条最容易踩、代价最大的规则（生成物不要手改、清单要同步、版本在几处必须同号…）；
4. **怎么验证**——确切的命令；以及**本环境的坑**（哪条会因环境而红、哪条要花钱/联网）；
5. **记录纪律**——改动要记到哪里、未做项记到哪里。

**反面案例**：某仓库根目录**没有**这个入口，唯一的同名文件是「要安装进用户目录的模板」——于是 agent 冷启动读到的是一份**教学协议**（「你是本 vault 的数学学习伙伴」，含「永不申请权限升级」这类与维护工作冲突的硬约束），而不是「这是什么仓库」。

### 2.2 文件的**名字**本身就是接口

自动发现机制按**文件名和位置**触发。于是「给用户用的文件」和「给 agent 用的文件」必须在命名上分开：

- 一个要装进**别人目录**的模板，如果占用了会被自动识别的文件名（例如安装后叫 `AGENTS.md`），那么它在**源仓库里**也会被当成「本仓库的指令」注入。
- **修法是改源文件名，不改安装名**：源文件叫 `vault-AGENTS.md`，由「安装清单」把它映射成目标名 `AGENTS.md`。消费方（安装器）遍历的是 `源 → 目标` 的映射，所以只改一个数据文件即可，逻辑零改动。

**判据**：凡是「面向别的仓库/目录的指令文件」，不要在源仓库里占用会被自动发现的文件名。**推论**：所有「向其他位置分发文件」的机制，都应当基于一张 `源 → 目标` 的**清单**，而不是散落在 N 处安装逻辑里的路径拼接。

### 2.3 长文档要有短入口

如果「必读」是几十 K token 的若干长文档，agent 会做两件坏事之一：**只读开头就动手**，或者**把预算烧在读文档上**。

**判据**：短入口（路由表：想知道 X → 读哪个文件的哪一节）+ 长文档（细节）。别指望 agent 顺序读完全部文档——**要让它能按需跳读**。

### 2.4 目录也是接口：全局文档不要放在子系统的文件夹里

**路径和文件名一样是接口**：读者用它判断「这文件是给谁的、要不要打开」。

真实案例：一个仓库的**交接文档**（入口地图 + 陷阱清单 + 唯一的「未做」清单）放在 `docs/memory/` 下。内容 100% 是仓库级的，但位置在说「这是记忆子系统的文档」。后果不是打不开，而是**该读它的人不读它**：维护者扫 `docs/` 时把它归进「记忆那摊事」，agent 冷启动时更容易整个跳过——**一个错位的目录，等于给最重要的文档加了一道隐形门槛**。

**判据**：问「**这份文档的读者是谁？**」答案是「任何要动这个仓库的人」→ 放 `docs/` 顶层（或根目录）；答案真的是某个子系统的维护者 → 才放 `docs/<subsystem>/`。

**移动一份已有文档的真实成本分布**（先知道再决定）：
- **便宜**：文件本身，`git mv` 保留历史。
- **中等**：引用。这个案例里 `handoff.md` 被 **~30 个文件引用、90+ 处**，且分三种形态——仓库根相对路径（`docs/memory/handoff.md`）、从 `docs/` 写的相对路径（`memory/handoff.md`）、从 `docs/memory/` 写的相对链接（`handoff.md`）。**逐类替换，别用一条正则通吃**；还要区分「链接目标」（必须改）与「散文里提到文件名」（不用改）。
- **最容易漏**：**文档自己的出链**。文件上移一层后，它原来的 `../x.md` 会指到仓库根去——移动后单独检查它内部的全部相对链接。
- **最容易「假成功」**：**用 `String.replace("a", "b")` 做批量替换**——它**只替换每个文件的第一处匹配**（要 `replaceAll`，或用带 `g` 的正则）。症状极隐蔽：一个表格里**文字标签更新了、链接目标没更新**，看起来像改好了；只有「改完再扫一遍旧串」这一步会把剩下的十几处揪出来。**批量替换的验收标准是「旧串计数为 0」，不是「跑过了」。**
- **必须做**：**给旧路径加守卫**（见 §2.2 的同一手法）。

**同一次会话里同一判据又用了三次**：退役规划稿从根目录移到 `docs/archive/`、宣传稿移到 `docs/promotion/`、而一份「事实上已经长成仓库级账本」的 `docs/memory/changelog.md` 提升到 `docs/changelog.md`。**判据相同（读者是谁）→ 处置也相同（移位 + 改引用 + 加守卫）**，守卫因此从一条规则长成一张「旧路径 → 新位置 + 理由」的表。两条附带经验：
- **大小写不敏感的文件系统会挡路**：想把 `changelog.md` 放到根目录时，它与已有的 `CHANGELOG.md` 在 Windows/macOS 上是**同一个文件名**，git 直接坏——所以它落到 `docs/` 顶层，与同样被提升的 `handoff.md` 并列。**移动前先问：目标位置和现有文件会不会撞名（含只差大小写）？**
- **被 `.gitignore` 命中的文件移动后仍然被忽略**（本例的宣传稿）：`git mv` 会报 `not under version control`，这不是缺陷，而是「刻意不入库」在生效。此时移位只整理工作副本，**引用它的文档对新克隆是散文提及**——所以要么保持无链接（本例实测 0 处链接），要么在该目录放一个说明文件，免得读者去找一个永远不存在的目录。

**「移动过的路径」要像「改过的名字」一样守**：未更新的旧路径是最常见的死链形态，而且它**不会报错**——只是让人点空、让 agent 找不到东西。守卫写法与改名守卫完全一致：一条正则 + 一份「路径 + 理由」白名单（历史档案可能需要引用旧路径）。这个案例里 `check-rename.mjs` 因此攒出三条规则：旧的 profile 名、旧的**产品名**、旧的**文档路径**——**三种「曾经的接口」用同一个守卫管**。

## 3. 真相源：单一事实 + 互相守卫

### 3.1 生成物必须带门禁

「提交进仓库的构建产物」（打包后的 JS、生成的 schema、编译出的清单）是最容易腐烂的东西：源码改了它不重新生成，**所有门禁依然全绿**，而它正是实际被消费的那份。

**判据**：每个提交进仓库的生成物都要有**再生成门禁**，做法是让守卫**调用生成逻辑本身**并逐字节比对（不是让守卫抄一份生成参数——那是第二份真相源）。

- **重构要点**：把「生成」从脚本的顶层副作用改成**可导出的函数**（`buildX() → 文本`），CLI 只负责写盘。守卫 import 它即可复用同一份逻辑。
- **注意换行符**：Windows 检出可能把文本文件变成 CRLF，而生成器产出 LF，逐字节比对会在**正确的**树上报「过期」。比对前两侧都归一化（这类坑值得写进入口文档，否则下一个人会再踩）。
- **注意环境**：生成物若需要子进程（打包器），在受限环境里会失败——按 §1.4 降级为 SKIP，**但形状检查仍要跑**。

### 3.2 清单要完备（新增即报错）

如果「哪些文件要被打包/安装/嵌入」是一张手写清单，那么**新人（或 agent）加文件时一定会漏**，而漏掉的后果往往不是报错，而是**静默少了一块**。

**判据**：清单要配完备性门禁——扫描源目录，任何「应当被纳入」的文件必须**要么在清单里，要么在一张「明确排除 + 写明理由」的表里**。两者都不是 → 构建失败。

- 实测收益：一个构建脚本此前只是「读这 13 个文件」，没有任何东西检查这 13 个是不是全部；加了完备性门禁后，新增一个未声明的模块会**立刻构建失败**并提示「加进清单，或写明为什么它不该进」。
- **配套门禁**：清单的键若会被「平铺落地」到同一目录，还要检查**不许有同名**（两个源文件同名会互相覆盖）。

### 3.3 「双份实现」要显式化，不能靠注释

有些代码结构上**无法共享 import**（不同运行环境、不同依赖注入方式），于是存在两份实现。危险不在于重复，而在于**静默漂移**：改了一份忘了另一份，两边行为分叉，而两个产物都"能跑"。

注释里写「keep the two in sync」是**没有约束力的**。

**判据**：加一致性守卫，把「静默漂移」换成「**显式决定**」：
1. **钉住共享清单**（哪些同名符号本应一致）——增删都必须是有意的；
2. 逐符号比对**词法流**而不是原始字节（注释、引号风格、`export`、空白都不算漂移——否则会淹没在误报里）；
3. 允许**有记录的偏离**：每条偏离写明理由；
4. **反向也要管**：已登记的偏离如果**已经一致了**，同样失败——否则豁免清单会腐烂成「随便漂移」的通行证；
5. 守卫自带提取器的**自测**（提取器自己有 bug 的话，守卫会撒谎）。

**注意顺序**：先做守卫、再谈去重。让漂移可见是前提；盲目合并两份已经分叉的实现，会把**行为差异**当成噪音抹掉。

### 3.4 同一个概念的散落定义

比"整份文件重复"更隐蔽的，是同一个决策散落在多处：权重阶梯、默认值、路径解析顺序、日期格式、`isInside` 判断……

**判据**：凡是「同一个事实被写了两遍」的地方，问一句：**改了 A 会不会忘 B？** 会 → 要么合并，要么加守卫。特别要查**测试/探针与产品逻辑的重复**——探针抄了一份产品公式，产品改了权重、探针没改，于是「探针全绿」在测一个**不存在的产品**。

最有价值的修法不是改数字，而是**让探针调用产品的同一份实现**（把管线抽成可导出的函数）。

**散落定义的终极形态：一条「边界规则」被复制 N 次。** 最危险的不是公式，而是**划分结构边界的规则**——「元数据块从哪到哪」「哪些行属于这个区块」。这类规则复制 N 份之后，**写入方与读取方对边界的理解一旦不同，产出的就是损坏的数据**，而且每一份单独看都合理。真实案例：判断 frontmatter 边界的正则在一个仓里被复制了 **15 次**，落在 6 个解析器里；该仓历史上最严重的三次数据损坏都是同一个形状（闭合分隔符落到了文件中间）。

修这类问题时，**「能不能共享 import」决定修法**，先查清这个约束：

| 情况 | 修法 |
|---|---|
| 所有副本都能 import 同一个模块 | 抽出去，全改调它（本节前半段） |
| 有一份**结构上无法** import（不同运行时、依赖注入、构建期内联） | **一份规范 + 少数必要拷贝 + 一条「行为等价」守卫**。硬凑成一份往往要改构建/注入契约，风险大于收益 |

**「行为等价」守卫比「文本一致」守卫更适合这类场景**，因为两份副本的注释与风格**本来就不该强求相同**，必须相同的是**判定结果**：把两份实现跑过同一组 fixture（含空值、CRLF、行尾空格、无尾随换行、特殊字符、非首块、未闭合，以及**每种结果各至少一个用例**）并比较输出。要点：

- **配对依据是「守卫要防哪种分歧」**，不是「有没有同名」或「文本像不像」。按名字配对的守卫看不见改了名的重复实现；按文本配对的守卫会把无害的风格差异淹没成误报。
- **守卫要放过文档**：只扫代码、跳过注释行。判据是「**运行时能不能与另一个副本分歧**」——文档引用那条规则是在解释它，运行时不可能与读者分歧。否则守卫会把自己解释规则的注释、审计报告、交接文档一起判违规（这种误报会让守卫很快被关掉）。
- **改一条没人测的路径之前，先给它加测试**：如果那条路径（例如某个模块被构建工具「剥掉导出语句再求值」的加载方式）当时**零覆盖**，而你正要改的恰好是它的接口，先补覆盖再改。这是「改完才发现坏了」与「改之前就知道没坏」的区别。

### 3.5 清单类文档：守卫必须**双向**核对

环境变量、配置项、路由表、支持的参数——这类"清单"最容易被写成一份**只往一个方向核对**的文档：代码加了新项、没人想起来写文档；或者更常见的是**反向腐烂**——文档里列着早就删掉的东西，读者照着它去调一个不存在的开关。

**判据**：任何"代码 ↔ 清单"的对应关系，守卫都要查三个方向：

| 方向 | 症状 | 严重度 |
|---|---|---|
| 代码有、清单无 | 新变量/新路由**不可发现**——维护者要 grep 才知道它存在 | 中（缺失） |
| 清单有、代码无 | **反向腐烂**：清单变成"曾经存在过的东西"的墓地，读者被引向不存在的开关 | 中（误导） |
| **标成"未实现/已废弃"的项又被读** | 有人**实现了**那个死开关，而所有人都以为它一直是死的 | **高**（沉默的行为变化） |

第三条是这类文档最容易被忽略、也最值钱的一条：它把"**将来实现这个死开关**"变成一次**必须同时改文档**的动作。真实案例：某仓 11 个环境变量散在 9 个文件里，夹着三对别名与一个"文档里被描述过、却没有任何代码读取"的开关；加守卫时三条规则各做了一次变异验证（删一行文档 / 加一行幽灵变量 / 真去实现死开关，各触发一条）。

**两条实操要点**：

- **清单要从代码里提取，不要凭记忆写**：写个脚本 walk 文件系统 + 正则提取，再拿结果去写文档。这既避免了漏项，也顺带纠正了记忆里的数字（真实案例：报告说"10 个变量"，提取结果是 **11 个**）。
- **守卫要显式跳过它自己**：守卫的注释里往往必须写出被禁止/被统计的**模式本身**（例如 `process.env.X`），否则它会把自己的说明文字算成一次命中。这与"守卫要放过文档"同源——判据始终是"**运行时能不能真的发生**"。

## 4. 安全与边界：锚在服务端，测试"未配置"

### 4.1 约束必须锚在服务端自己的状态上

「调用方声明的东西，永远不能成为约束调用方的依据。」

- 实测漏洞：某面板接口的「允许根目录」在两个环境变量都没设时**退回请求里带的路径**。于是下游「目标是否在允许根之内」的两端**都由调用方决定**，约束形同虚设。
- 修法：允许集合 = **服务端自己的配置 ∪ 服务端运行时已知的注册项**；两者都空 → **拒绝一切带该参数的请求**（fail-closed）。

### 4.2 「未配置 / 空值」分支必须有测试

上面那个漏洞能存活，是因为**测试套件在它之前的每个用例都先设了环境变量**，恰好绕过这条分支。

**判据**：每一条 `if (!configured) …` / `?? fallback` / 空数组 / 空字符串分支，都要有一个**走到它的**用例。**没有用例走到的分支，不算被测过。**验证方式仍是变异验证：把旧的（错误的）逻辑还原，那个新用例必须失败——如果还原后测试还是绿的，说明这个用例根本没走到那条分支。

## 5. 文档：区分「当下的声明」与「历史的记录」

文档腐烂有类型学，处理方式完全不同：

| 类型 | 例子 | 处理 |
|---|---|---|
| **当下的声明** | 「当前版本是 x.y.z」「本功能默认开启」「状态：提案」 | **必须与代码一致，并加守卫** |
| **历史记录** | 变更日志、「0.7.2 时做的事」「上一版是 0.7.1」 | **不要追改**——改了会让「为什么变成现在这样」失真 |
| **计数** | 「回归 232 项」「8 条路由里 4 条有测试」 | 尽量让守卫与**运行时实际计数**挂钩 |
| **验收声明** | 「已验证支持 X」 | 只写**已提交的证据**支持的结论 |

### 5.1 声明要「可被机器判定」

一条「状态：提案（未实现）」如果实际已实现，读者（人和 agent）无法分辨该信谁。**修法不是改一个词，而是让它可判定**：

- 版本横幅用**精确标记行**（版本号独占一行，如 `> 当前版本：0.7.5`），由守卫与包清单比对；
- **用精确标记而不是宽松正则**，是为了不把「0.1.5 adaptation」「0.7.2 时…」这类**历史引用**误判成当下的声明；
- 数量类声明锚到**运行时计数**（并因此享受 §1.3 的红利：计数一自数，文档锚点就跟着变可信）。

### 5.2 历史记录不要改写

一个可维护的仓库通常有两层记录：**面向发布的摘要**（改了什么）和**面向维护者的细账**（为什么改、怎么改、踩了什么坑）。改名、重构、纠错都应写在**新条目**里，而不是回去修历史条目。

**判据**：如果你发现自己在追改历史记录，先问「未来的读者需要知道『当时是那样』吗？」——通常需要。**把更正写在新的地方，并指向历史。**

### 5.3 「已归档/已退役」的文件里，仍可能藏着一句当下的声明

退役档案最容易被漏掉：它的**正文**是历史，但**状态横幅**（"Phase X 未做""状态：实施中""本文件描述的方案待定"）是关于**现在**的声明。这类横幅腐烂得最久，因为"已退役 = 不用维护"会让所有人不去看它。

处理方式按文档类型分三种，别一刀切：

| 文档类型 | 正文 | 状态/结论 |
|---|---|---|
| **日期化审计/快照**（`*-assessment-<日期>.md`、调研笔记） | **不动**——它是"当时的证据" | 加**日期化更正块**，写清"现在是什么、权威依据在哪" |
| **已退役的规划稿**（`docs/archive/REFACTOR-PLAN.md` 之类） | **不动** | 更正**横幅**：把"未做"改成事实，并区分"这个形态未做"与"这件事后来换形态做了"——否则一个笼统的反转会把半对的说法改成另半错 |
| **活文档** | 直接改 | 直接改 |

**特别小心「半对」的陈旧声明**。「Phase 4 未做」可能一半是真的：那个**形态**（自挂 DOM 列）确实没做，但需求后来**换形态**（官方槽位）交付了。遇到这种，先查清"未做的是需求还是实现"，再动笔——**笼统地反转结论，等于制造一条新的错误声明**。

### 5.4 「全仓排查」不能用 grep 收尾

想证明"仓库里没有 X"时，**不要用 `grep`**：它会跳过隐藏目录与 `.gitignore` 命中的文件，于是 `.deepseek/`、`.github/`、fixture 目录里**被跟踪的**文件全在盲区。真实案例：一次改名排查中 grep 报 28 处、而遍历文件系统的守卫多报出一处——它在 `scripts/qa/benchmark-vault/.deepseek/` 里，是 **git 跟踪的文件**。

**规则**：`grep` 用于**定位**，不用于**证明不存在**。要下"全仓没有"的结论，写一个**自己 walk 文件系统**的守卫，并且：

- 把"跳过了哪些路径、为什么"写成代码里的**显式白名单 + 理由**（不是默默跳过）；
- 白名单分两类：**历史档案**（旧名是事实）与**冻结语料/fixture**（改了会改变测量结果）。后者其实是一条「刻意不改」的决定，应同时记进未做清单。

这样"不改历史"就从习惯变成了**需要显式决定并写下理由**的事——下一个人想改，会先看到理由。

## 6. 记录纪律（让下一个人/下一个 agent 能接手）

1. **未做清单是唯一的。** 所有「没做 / 待定 / 已知未修」集中在一个权威位置，并带优先级。散落在各文档的「TODO」等于没有 TODO。
2. **台账可追溯。** 一份审计/整改报告要能追到「哪条 → 改没改 → 凭什么相信」。证据要具体到**命令 + 观察到的结果**（含变异验证的那句报错）。
3. **陷阱要成文，且写清根因。** 「不要这么写」没用；「这么写会在 Windows 上因为 CRLF 误报，修法是读入即归一化」才有人（和 agent）记得住。
4. **明确记录「刻意没改」的东西。** 为什么没改（需要用户决定、属于历史记录、结构性偏离）和改了什么一样重要——否则下一个人会把它当漏项重做一遍。
5. **区分「已知偏离」与「待修 bug」。** 前者是决定，后者是工作项。混在一起，两个都会烂。

## 7. 怎么给 agent 派活（维护者视角）

- **先要求它读入口文档 + 跑一次全量门禁**，并把输出贴回来。门禁不可信之前，任何改动都是在盲改（§1）。
- **验收标准写成「可观察的证据」**：「跑 X，看到 Y」，而不是「修好 Z」。让它在报告里附命令与输出。
- **要求变异验证**：改完守卫类代码后，让它故意制造缺陷、证明守卫会失败、再恢复。这是对抗「看起来很对」的最便宜手段。
- **明确边界**：哪些动作不能做（推送、打 tag、发布、动真实用户数据、烧钱的 E2E）。**"要不要花钱/联网"要显式问。**
- **要求它区分「代码的问题」与「环境的问题」**——这是 agent 最容易搞错、代价又最大的一类判断（它会去"修"一个在它环境里根本跑不了的东西）。
- **一个提交只做一件事。** 便于审查，也便于回滚。修 bug 与重构不要混在一个提交里。**但真正决定成败的不是这条原则，而是「什么时候提交」——见 §7.1。**

### 7.1 提交粒度：把改动切成「能被单独理解、单独回滚」的单位

**最贵的错误是「攒着」。** 一个 agent 连续做完 8 个主题、跑了 8 次门禁，最后把 63 个文件的改动一次性提交——此时「按内容分次提交」**已经不可能干净地做到**了：

- 同一个文件往往同时装着多个主题的改动（测试文件里有新用例 + 计数修正 + 改名），要拆只能逐 hunk 挑选，成本高且容易挑错；
- **汇总型记录文件**（CHANGELOG、交接文档、变更账本）**天然横跨所有主题**，除非逐 hunk 拆，否则必然整体落在某一个提交里。

**所以做法是反过来的：每完成一个「已验证的内聚单元」就提交一次。** 这样天然的边界就是内聚的，不需要事后外科手术。判据很朴素：**门禁刚跑绿、而这次改动还能用一句话说清 → 提交。** 「等全做完再整理」这个念头一出现，就已经晚了。

**一次提交的检查清单**：

1. `git status` 里只应有**这一个主题**的文件。混进别的主题 → 只 `git add` 你要的，其余留着。
2. **`git diff` 看一眼你没主动改的文件。** 它可能装着**别人的在途工作**。这个案例里 `package.json` 看着"不属于本轮"，查过之后发现改动确实是本轮的（`test` 指向新的门禁汇总器）——**但"看起来不属于我"必须查证，不能默认**。若确实是别人的在途工作：**单独一个提交 + 报告里点明**，绝不混进自己的主题。
3. 首行 `<type>(<scope>): <一句话>`；**正文先讲"为什么"，再列"改了什么"**。半年后来 `git bisect` 的人，先看的是为什么。
4. 提交**之后**再跑一次门禁：漏带文件、多带文件都会被 `git status` 暴露出来。

**汇总型文档怎么放**：仓库惯例通常要求「代码与文档同提交」，但 CHANGELOG / 交接文档 / 变更账本这类**聚合**文件无法按主题切分。做法是给它们**单独一个 `docs(...)` 提交**，并在正文里说明它覆盖前面哪些提交——**把"无法切分"写成显式的说明，而不是假装它属于某个主题**。

**给 agent 的实务细节（都踩过）**：

- **不要指望 heredoc**：`git commit -F - <<'MSG'` 在 PowerShell 里是语法错误。把消息写进文件再 `git commit -F <file>`；文件放 `.git/` 下面，既不污染工作树，也不会被自己的守卫扫到。
- 用 `git mv` 而不是「删一个、加一个」，历史才跟得过去。
- **一条命令跑完就确认结果**（`git log --oneline -1`、`--stat`），别攒一批命令再一起看——批处理里的一个语法错误会让**整批**都没执行，而输出看起来像"跑过了"。

## 8. 接手一个仓库时的检查清单

**可信度（先做这个，别急着改代码）**

- [ ] 跑一次全量测试。**红的是代码问题还是环境问题？** 逐条判定。
- [ ] 测试入口是「跑完全部再汇总」，还是 `&&` 链？（后者 → 现在有多少条被静默跳过？）
- [ ] 有没有子进程/解析输出型的守卫？它区分「跳过 / 跑不起来 / 真结果」吗？
- [ ] 打印的分母是自数的还是手写常量？
- [ ] 有没有**提交进仓库的生成物**？它有没有再生成门禁？我能不能靠本地命令发现它过期？

**入口**

- [ ] 仓库根有给 agent 的入口文件吗？它讲的是**数据流与文件地图**，还是愿景？
- [ ] 有没有「安装进别人目录」的文件占了会被自动发现的文件名？
- [ ] 必读文档多大？有按需跳读的路由表吗？

**真相源**

- [ ] 同一事实写了几遍？（默认值、权重、路径解析顺序、日期格式、`isInside`…）
- [ ] 有没有两份无法共享代码的实现？它们靠什么保持一致——注释，还是守卫？
- [ ] 「哪些文件要被打包/安装」是清单吗？清单有完备性门禁吗？

**安全**

- [ ] 约束（允许路径、允许来源、权限）锚在**服务端状态**上，还是锚在调用方给的参数上？
- [ ] `未配置 / 空值` 分支有用例走到吗？（变异验证：还原错误逻辑，用例会红吗？）

**文档**

- [ ] 有没有「当前版本/当前状态」这类**会腐烂的声明**？它们可被机器判定吗？
- [ ] 历史记录有没有被追改的痕迹？（有 → 说明记录纪律没定清）

**记录**

- [ ] 未做清单在哪？唯一吗？带优先级吗？
- [ ] 审改台账能追到证据吗？

## 9. 反模式速查

| 反模式 | 后果 | 对症 |
|---|---|---|
| 守卫把「没跑起来」当成「结果错了」 | agent 去改**正确**的东西 | 四态：通过/失败/按设计跳过/环境不可用 |
| `cmd1 && cmd2 && …` 长链 | 首个环境性失败吞掉后续全部信息 | 汇总器：全跑 + 逐项状态 + 失败尾部 |
| 手写的测试分母 | 「全绿」只是算术；错数字扩散到文档 | 断言函数内部自数 |
| 无再生成门禁的构建产物 | 产物腐烂而门禁全绿 | 守卫调用生成函数逐字节比对 |
| 守卫抄一份生成参数 | 第二份真相源，自己先漂移 | 生成逻辑导出为函数，双方共用 |
| 手写的「要包含哪些文件」清单 | 新增文件静默漏掉 | 清单 + 完备性门禁 + 明确排除表 |
| 「keep in sync」注释 | 静默漂移，两个产物都"能跑" | 一致性守卫 + 有记录的偏离 + 反向腐烂检查 |
| **边界规则**（"块从哪到哪"）被复制 N 次 | 写入方与读取方对边界理解不同 → **损坏数据**（且每份单独看都合理） | 规则收进唯一实现；无法 import 的那份用**行为等价**守卫（同一 fixture 集比结果） |
| 守卫按**名字**或**文本**配对 | 改了名的重复实现是盲区；无害的风格差异淹没成误报 | 按"要防哪种分歧"配对；比行为而不是比 token |
| 清单类文档只往**一个方向**核对 | 反向腐烂：文档列着已删除的项，读者被引向不存在的开关 | 双向核对；**"标为死开关的项又被读"必须失败** |
| 守卫扫描范围包含文档/注释 | 误报解释规则的文档，守卫很快被关掉 | 只扫代码、跳过注释行；判据是"运行时能否与另一副本分歧" |
| 改了零覆盖的加载/构建路径 | 改完才发现坏，且没人会知道 | 先给那条路径补覆盖（含一次真实调用），再动代码 |
| 探针/测试复刻产品公式 | 探针在测一个不存在的产品 | 抽成共享函数，双方调用同一份 |
| 约束锚在调用方给的参数上 | 安全边界形同虚设 | 锚在服务端状态；空则 fail-closed |
| 未配置分支无用例 | 漏洞在最"边角"处存活 | 每个 `!configured` 分支都要有用例 |
| `AGENTS.md` 之类被自动发现的文件名给了"给别人用"的文件 | agent 被注入**错误的**指令 | 源文件名与安装名分离（清单映射） |
| 追改历史记录 | 「为什么变成现在这样」失真 | 更正写在新条目并指向历史 |
| 退役档案里的**状态横幅**（"Phase X 未做"） | 它以"已退役"为名逃避维护，却在下**当下**的判断 | 正文不动、横幅按事实更正；**半对的声明要区分"需求未做"还是"这个形态未做"** |
| 用 `grep` 收尾"全仓排查" | 隐藏目录/被跟踪的 fixture 全在盲区，结论是假的 | 用自己 walk 文件系统的守卫；跳过项写成**显式白名单 + 理由** |
| 只写「已实现/已修复」不附证据 | 无法区分「改好了」与「以为改好了」 | 命令 + 输出 + 变异验证的报错 |

## 10. 最小可执行版本

如果只做三件事：

1. **让全量测试在受限环境里也可信**——汇总器代替 `&&` 链，四态代替红绿，计数自数。**这一步没做完，其它所有工作的收益都是不可验证的。**
2. **写一份三十秒入口**——数据流 + 「改 X 必做 Y」文件地图 + 验证命令 + 环境坑。
3. **给每个提交进仓库的生成物加再生成门禁**，并**做一次变异验证**证明它会失败。

做到这三件，agent 就从「能读代码」变成「**能在闭环里工作**」。剩下的（双份实现去重、巨型函数拆分、文档瘦身）都是在这之上才谈得上的优化——**顺序反了，优化出来的东西没人能验证。**
