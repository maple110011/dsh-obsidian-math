## 2. 第二组：家族协议与路线

| # | 事项 | 选项 | 代价 | 我的建议 |
|---|---|---|---|---|
| **P3** | **research profile 的姿态放宽到什么程度** | ① 默认全关，安装时由你逐项 opt-in ② 预置两档（保守 / 放开）让你选 ③ 一次全开 | ①最安全但要你每次配置 ③最省事但把"放宽"变成默认 | **①**：默认全关 + 安装时选项。理由：dsh 的权限 preset 是**闭表**，姿态只能由 profile 定；"放宽"不该是默认值 |
| **P4** | **是否接受"派生索引"落地为 `node:sqlite` / 向量文件**（L2 拆半的具体化） | ① 接受，按"可重建、非必要、非契约"三条规则 ② 只接受 JSON 缓存（现状）③ 不接受 | ①引入**第二套存储的生命周期**（谁建/失效/重建/schema 漂移），是**新维护面** ③ 语料一大就退回"每次全扫" | **①**。理由：**`node:sqlite` 本机内置可用**（实测 `DatabaseSync/StatementSync/Session/backup`，零新依赖）；而三条规则把"第二个真相源"的风险摁住（**删掉索引必须能重建且功能不降级**是可执行断言） |
| **P5** | **是否建可复现的质量/成本基准**（L6 前半反转） | ① 建（照 `archive/cost-benchmark-2026-08.md` §5 的五个条件）② 暂不建 | ①要修好**当前的坏度量**（token 计量读错事件、`baseline.json` 只写不读）并写固定用例 ②目标变成"质量"却无法判定改进 | **①**。理由：省钱的年代可以不量；**目标改成质量之后，"无法验证的改进"不接受** |
| **P6** | **契约包的包名/scope，以及是否转 monorepo** | ① 先"同仓库多目录 + 各自 `dsh.bundle.patch`"，第 2 个包稳定后再转 monorepo ② 现在就转 ③ 不建契约包 | ①要接受一段"半结构化"期 ③第三方贡献无从谈起 | **①**。契约包必须先有（§2.2），但**仓库结构可以晚一步**——dsh 支持 `dsh plugin add file:<dir>`，多目录已达同样交付语义 |
| **P7** | **第三方贡献开放到哪一层** | ① 只开放**能力包**（不改数据契约）② 也开放**数据契约扩展** | ①扩展性受限 ②影响**所有**成员与用户的既有 vault，必须有迁移+fixture+幂等断言+契约 owner 复核 | **①起步，②需更严审批**。先把"提能力包"这条路走通，再决定要不要放开数据面 |

## 4. 蓝图里**已经不需要你拍板**的部分（我按现有证据定了）

- **数据契约版本化的模型**（§4.2）：直接借 dsh 自己的会话格式迁移模型（**一跳一个迁移包**），因为它是上游现成做法，没有取舍空间。
- **一页式兼容协议**（§4.5）与**命名/前缀/版本下限**规则：照 dsh-web 已在 8.2k star 规模验证过的做法。
- **收编与许可红线**：无 LICENSE / 未授权 / 版权不明 ⇒ 不收编——这是法律底线，不是偏好。
- **`ctx.jobs` 不能当调度器**、**hook 协议不适用于 native 插件**、**权限 preset 是闭表**：都是 0.2.0-rc.2 的实测事实，不是选择。
