# 检索 v3 提案（第二版：端到端审视 + 「统一入口、粗筛-精读」架构）

> 状态：**已实现并两层验收**（引擎探针 12/12 + 真实会话 E2E 4/4，见 §6 与 docs/memory/testing.md）。背景：用户明确「现状不必维持、完全推倒重来可接受，优先保证 AI 正确且快速检索到相关信息，愿意花 tokens 保效果」。
> 依据：AgentIR（2603.04384）、RaDeR（2505.18405）、LeanSearch v2（2605.13137）论文笔记见 references.md §7-9；GraphMemix（2608.26983）的吸纳决策与 A/B 测量见 **§7**；对检索/关联/提取/整理四层代码与真实 vault 状态的逐行审视。

## 1. 检索的本质（决策者速读）

- 上下文装不下整个 vault，任何方案都必须「先选、后读」。
- 「让 AI 全局检索」是一个循环：想清楚查什么 → 选候选 → 读候选 → 判断 → 不够则换查询。「打分器」只是循环里「选候选」的排序规则，二者不互斥。
- 三种排序器对比：

| 排序器 | 能力 | 成本 | 角色 |
|---|---|---|---|
| BM25（词法） | 词面匹配，稀有词加权/词频饱和/长度归一 | 0 token、0 部署、毫秒 | 经典强基线，粗筛 |
| 本地 embedding | 语义相似（词面不同意思相关也能召回） | 0 token、约 95MB 模型 | 扩大粗筛召回 |
| LLM 重排 | 亲自读候选判相关，最准 | 按候选数烧 token | 精读/挑选环节 |

- 最优组合（LeanSearch v2 同构）：**粗筛（BM25 宽网 top-50）→ LLM 精读挑选（50 条一行摘要中挑 2-3 篇读全文核实）**。正确性 = LLM 判断兜底；速度 = 只读 2-3 篇全文；成本有界。

## 2. 端到端审视结论（四层）

### 检索层（问题最重）

1. 四条检索路分裂：grep（子串）、note_search（子串+tag，无排序）、note_retrieve（hook 打分，只看记忆卡）、召回注入（最新消息原文对四类语料排序）——AI 靠 AGENTS.md §5 手写路由表选工具，查一个主题需笔记与记忆分两次查；
2. note_search 无相关性排序，命中按文件序返回；
3. 召回注入每轮无条件烧 2200 字符，且与工具检索是两套不相干的排序；
4. hook 卡只覆盖记忆，普通笔记不参与策略检索。

### 关联层

5. 关联全靠三写自律（wikilinks/related/source）；实测 vault records/index.md 为空——三写第 2 步在真实使用中未落地，关联层半失效；
6. 无确定性断链检查（source 悬空、related 断链、索引缺行）。

### 提取层

7. 提取 = 模型收尾三写（prompt 自律）；实测 episodes/memos 质量高，但记录层零产出——「细→粗」链条断在第 2 环；
8. 审计 pass 管 hook 统计，不管结构校验（缺 source/缺索引行）。

### 整理层（健康，保留）

9. 五层结构、每日体检、hook 统计回写、归档：不动。

## 3. 目标架构：统一入口 + 粗筛-精读

```
┌─ 统一索引（本地，毫秒构建/更新）──────────────────────┐
│ 每篇一个 passage：笔记 + 记忆卡 + 备忘录 + 主题/事件行   │
│ = 标题 + tags + 摘要/首段 + hook 字段 + source/related    │
└────────────────────────────────────────────────┘
        │ ① 粗筛：BM25 top-50（0 token，毫秒级）
        ▼
  50 条一行摘要（title + 一句话，有界 ≈1-2K token）
        │ ② 精读：AI 在生成内挑 2-3 篇读全文核实 ← tokens 花在这里
        ▼
  不够/全不适用 → 改查询重试一次 → 仍无 → 明说没有（空是信号）
        │ ③ 顺链：读到的笔记/卡沿 related/source 链扩一步
        ▼
  ④ 可选扩召回：本地 bge-small-zh hybrid；独立 LLM 重排为备选开关
```

### S1 统一索引与统一入口

- 新工具 search（暂名）一次覆盖笔记+记忆卡+备忘录+主题/事件；返回带来源类型标注的统一 top-k；
- AI 不再背路由表；hook 命中统计（uses/last_used）迁移到 search 的命中记录，反馈闭环不丢；
- 索引按 vault 文件 mtime 指纹增量重建（现有 recall 缓存的机制复用）。

### S2 粗筛：BM25

- 标准 BM25（k1=1.2, b=0.75）+ 现有分词（ASCII 词 + CJK 二元组）；hook 字段加权（techniques/applications 命中加分）；
- 零 token、零部署、毫秒级；比现状 overlap 系数严格更强（词频饱和+长度归一）。

### S3 精读：LLM 在生成内挑选核实（正确性核心）

- search 返回 top-50 的一行摘要列表（有界 token）；AI 在自己的推理里挑 2-3 篇读全文并逐篇判「适用/不适用」；
- 全部不适用 → 换查询重试一次（有界）；仍无 → 明说没有——LeanSearch 的「空集是信号」；
- 这是 AgentIR「推理联合查询」+ LeanSearch「reranker」的零额外 API 调用版本：挑选发生在主生成内。

### S4 可选扩召回（按探针结果启用）

- 本地 bge-small-zh（约 95MB，transformers.js，CPU 毫秒）：hybrid = 0.5×BM25 + 0.5×cosine，覆盖「策略相似词面不同」漏检；
- 独立 LLM 重排（每次检索 1-2K token）：仅当用户明确要求更强效果时启用。

### S5 注入改为按需导航

- 每轮只注入极简「主题地图 + 最新事件标题」（几百 token），让 AI 知道「有什么」；细节全部走 search；
- 替换现在的 2200 字符无条件召回注入——更省、且与工具检索同一排序。

### S6 关联顺链与提取校验

- 精读环节顺链：读到的笔记/卡沿 related/source 链扩一步（一次 search + 顺链读替代多次 search）；
- 审计 pass 增加结构校验项：records 缺 source、索引缺行、related/source 断链 → 注入体检报告，三写从纯自律变成「自律+体检兜底」。

## 3.5 架构边界：与记忆系统的关系（写读分离、文件契约耦合）

- **不合并、也不完全独立**：写路径（三写/体检/统计回写/归档）与读路径（索引/排序/精读）保持独立生命周期与故障域；两个系统只通过文件级接口耦合。
- 接口 ① 数据：检索系统把 `.deepseek/memory/**` 卡片当作「带类型的文档」纳入统一索引（与笔记同一管线，查询一次同时命中笔记与记忆）；检索**只读不写**记忆文件，安全边界不变。
- 接口 ② schema：hook frontmatter 归记忆系统拥有（模板 + 审计维护），检索系统消费（passage 组装 + 字段加权）；schema 变更 = 两系统唯一协调点，版本化。
- 接口 ③ 反馈：检索命中 → `cache/retrieval-stats.json` → 体检读统计并回写卡片 `uses/success_rate` → 检索读作先验。数据流成环，代码零互相调用（现状已如此，v2 保留）。
- 接口 ④ 推送：profile/topics 导航注入与 dialogue 线索由记忆系统注入 prompt（让 AI 知道「有什么」）；「拉取」全部走统一 search。
- v2 迁移点：note_retrieve 的 hook 打分与命中统计并入 search；算子硬过滤降级为可选参数；三写、体检、归档、捕获策略完全不动。

## 4. 成本模型（本 vault 规模）

| 环节 | token | 时延 |
|---|---|---|
| 统一索引构建/增量更新 | 0 | 毫秒-百毫秒（仅文件变化时） |
| 粗筛 BM25 top-50 | 0 | 毫秒 |
| 50 条一行摘要列表 | 约 1-2K | 即注入 |
| 精读 2-3 篇全文 + 判断 | 2-4K | 正常生成 |
| 按需导航注入（替代 2200 字符召回） | 数百 | 0 |
| **每轮合计** | **约 3-6K（有界）** | 本地毫秒 + 正常生成 |

对比现状：四路分裂检索 + 无条件 2200 字符注入，token 不省、注意力分散、笔记与记忆两查。

## 5. 兼容与迁移

- 旧工具去留：search 取代 note_search 与 note_retrieve 的查询职责（hook 统计迁移）；note_links 保留为顺链专用；grep 保留为底层兜底；

- 无 hook 旧卡片参与统一索引（BM25 覆盖全文），零迁移。

## 7. GraphMemix（Li et al. 2026）可吸纳点：决策与测量记录

> 来源：**GraphMemix: Query-Aware Evidence…**（arXiv:2608.26983）；卡片 `literature/cards/liGraphMemixQueryAwareEvidence2026.md`，精读记录 `literature/reading/liGraphMemixQueryAwareEvidence2026.md`（含全部超参与表 1-10），论文笔记见 `references.md` §12。
> 这一节回答两个问题：**它的哪些机制我们已经吸收**，以及**哪些机制经测量/权衡后不吸收、理由是什么**。凡「不吸收」都带数字或可判定的条件，避免下次重新讨论。

### 7.1 已落地的机制（不是本文档的新提案，见 §7.4 状态表）

| 机制 | 落点 | 文档 |
|---|---|---|
| 适用边界门控（`not_applicable_when`，对应论文的 anti-condition gate） | `buildRecallDoc` 读出 `boundary`，`rankRecallDocuments`/`rankStrategyCards` **硬排除**并返回 `excluded[]`；`note_recall` 渲染「另有 N 条因适用边界被排除（命中「…」）」 | `design-intake-2026-09-10.md` §1/§6 |
| `harmed`（负迁移计数） | `hook.harmed`；面板 `⚠️ 倒忙 N 次`；体检 `counts.harmed` | 同上 |
| `verified_by` 凭据见证 | `applyFeedback` 写 `verified_by: user`/`none`；体检 `structural.unjustifiedUpgrade` | 同上 |
| 声明值 vs 有效值 | `uses` = 声明 + 未合并增量，面板只显示有效值 | 同上 |
| `degraded` 替代静默成功 | 体检 `status`/`warnings`/`postconditions` + 读回核对 | 同上 |

### 7.2 测过之后决定不采纳：多视图 max-pool

论文的检索核心之一是**多视图打分 + max-pool**（同一文档按标题/摘要/正文分视图各自打分，取最大，避免长正文稀释短标题的精确命中）。

- 已实现为**可测量选项**：`composePassageViews()` 把 passage 拆成 `title` / `keywords` / `body` 三个视图（字段集合与单袋完全一致，唯一差别是池化方式），`rankRecallDocuments(docs, query, { viewPool: "max" })` 按视图各自的长度统计算 BM25 再取最大；`viewPool` 默认 `"bag"`，返回值里如实回报本次用了哪种池化。
- 探针 A/B（`npm run qa`，真实 vault，11 条 ground truth，top-8）：

| 口径 | bag（现状默认） | max-pool |
|---|---|---|
| Direct / Recoverable / No access | 11 / 0 / 0 | 11 / 0 / 0 |
| 目标排名（11 例均值） | **1.73** | 2.27 |
| 排名改善 / 变差 | — | 0 / **2**（Fubini-Tonelli 1→5，Helly 引理 3→5） |
| 有符号净恢复 Δ(max − bag) | — | **+0 − 0 = 0** |

- **结论：保持单袋默认。** max-pool 在本 vault 上没有任何收益，且把两例从 rank 1/3 推到 rank 5。原因是我们与论文的语料形态不同：我们的袋已经**按种类截断且有界**（正文 200-2000 字符），长度归一用的是语料平均长度，稀释效应本来就小；而 max 丢掉的是「查询词分散在标题与正文时两个视图的分数相加」这一信号——多词查询因此普遍掉分。
- 可判定条件（何时重新考虑）：探针出现 **Direct 数下降** 的案例，或某个真实查询出现「标题精确命中却排在第 5 名之后」的稀释现象。届时先补一条该现象的 ground-truth 用例，再复测 Δ。

### 7.3 不采纳：通用多样性/冗余重排（MMR、DPP）

论文的控制实验（其表 9/10）已给出反例：Top-K 56.87 vs MMR 56.84 vs DPP 52.69；有符号净恢复 forest +43 vs MMR −6 / DPP −36。多样性目标会把「同一技巧的多张卡」互相挤掉，而数学检索里这些卡恰恰互为证据。

- 我们的对应纪律已写进 `AGENTS.md` §5（「不要做『通用多样性』重排」）：需要的不是去重，而是**边界排除 + 弱信号诚实**。
- 唯一例外是既有的 `duplicate_of`/`superseded` 排除——那不是多样性重排，是**同一张卡的不同版本**。

### 7.4 记录在案、暂不实现（附触发条件）

| 机制（论文） | 我们的对应物 | 为什么现在不做 | 触发条件 |
|---|---|---|---|
| 查询条件化的关系信任 + 「锚点槽位」（`p_i − λc_e < p_i` 才让邻居占结果位） | `related`/`source` 边目前**无类型、未经核验**；顺链是模型在精读里自己走的（S6） | 把邻居自动塞进结果位会改变 note_recall 的语义，且我们还没有「边可信」的信号源 | 出现「命中卡正确但下一条证据永远看不到」的真实失败，且 `related` 边带上了可信度（可用 `verified_by`/`harmed` 当先验） |
| 自适应 k（按「打开成本」决定取几条） | 现在是固定上限（≤2 次 recall、每次读 ≤3 篇全文） | 这是语义设计（要拍板「不确定性换读取」的交换比），不是确定性改动 | 用户明确要求按难度自适应，且探针能测出「多读一条」的净收益 |
| 两阶段适用性判定（先粗判再精判，保守解析） | 现在只有硬门控 + 精读纪律 | 需要第二次模型判断，即「新增每轮必做步骤」——我们的实测失败模式是机制没人用 | 精读纪律在真实会话里被反复证明不够（要证据，不是感觉） |
| 可达性分层 + 有符号净恢复 Δ | **已实现为测量**（本文件 §7.5） | — | 已落地 |

### 7.5 可达性分层与有符号净恢复 Δ（已落地的测量方法）

`scripts/qa/engine-probe.mjs` 现在除了 12 组断言，还输出 §2 可达性分层：

1. 从 vault 原文抽取 `related`/`source`/`[[wikilink]]` 边（只认能解析到语料内文档的链接；断链不算可达），得到无向的一步邻接；
2. 每条 ground truth 目标分成三层：**Direct**（在 top-8 内）／**Recoverable**（不在 top-8，但与某个 top-8 命中一步相邻）／**No access**；
3. 对两种池化（bag / max）各算一次，报告 **有符号净恢复 Δ = 上升例数 − 下降例数**，以及目标**排名**的均值与改善/变差例数。

**为什么必须两者都看**：分层是粗粒度的——本轮 11/11 全是 Direct，只看分层会得出「两种池化完全一样」的结论，而排名显示 max-pool 实际更差（§7.2 表）。分层回答「够不够得到」，排名回答「够到得多快」，两者都是「先量再改」的输入。

**读法约定**（也是未来改检索的门槛）：改动检索必须给出「Direct 数不降 **且** 目标排名均值不升」的结果；只有分层改善而排名变差时，按未通过处理。

### 7.6 边界：我们与论文的形态差异（为什么不能整包照搬）

| 论文 | 我们 |
|---|---|
| 图数据库 + 多跳证据路径 + 查询条件化遍历 | 十来个纯文本文件 + `[[链接]]`；「图」是人可读的，不为机器遍历而存在 |
| 检索即「找证据路径」，召回质量靠图结构 | 检索即「选候选 → 模型读全文核实」，正确性由模型判断兜底（LeanSearch 同构） |
| 有符号净恢复是主指标 | 主指标是「模型读完是否正确」，探针只是零 token 的前置过滤 |
